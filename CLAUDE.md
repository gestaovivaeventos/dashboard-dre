## Architecture

**Stack**: Next.js 14 (App Router) + TypeScript + Supabase (Auth + Postgres + RLS) + shadcn/ui + Tailwind CSS. Deployed on Vercel with Cron Jobs. AI features use the Vercel AI SDK (`ai` + `@ai-sdk/openai`, model `gpt-4o-mini`).

**What it does**: Internal management platform for Grupo Viva, split into **two modules** that share one auth/session layer:

1. **DRE Financeiro** (`(app)` route group) — Income-statement dashboard. Syncs Omie ERP data, maps Omie categories to DRE accounts, computes KPIs, cash flow, budget/forecast, and AI-generated executive reports. Multi-company and multi-segment.
2. **Controladoria / CTRL** (`(ctrl)` route group, URLs under `/ctrl`) — Purchase-requisition + accounts-payable workflow: requests → budget check → manager/director approval → supplier registration → launch into Omie *contas a pagar*.

Both modules are gated by the same session context; a user can have access to one, both, or neither.

### DRE data flow

```
Omie ERP API → financial-processor.ts (11 rules) → financial_entries table
Google Sheets (FEAT, Terrazzo) → sheets/*-sync.ts ─┘   ↓
                              dre_monthly_aggregates / cash_flow_monthly_aggregates (materialized)
                                                          ↓
                                  dre.ts / cash-flow.ts (aggregation + formulas)
                                                          ↓
                              Dashboard / KPIs / Fluxo de Caixa / Budget / AI report / PDF export
```

`financial_entries` is the cash-basis source of truth. The `*_monthly_aggregates` tables are pre-computed rollups refreshed by `src/lib/dashboard/aggregate-refresh.ts` (with a statement-timeout guard) — read paths prefer the aggregates, not raw entries.

**As `refresh_*` só aceitam `service_role` desde a auditoria de 03/09/2026 — chame-as com `createAdminClientIfAvailable() ?? supabase`, nunca com o client do usuário.** O refresh é best-effort e engole erro, então com o client errado ele falha em silêncio e o agregado fica defasado até o próximo sync, sem ninguém ver. As rotas de mapeamento de categoria DRE ficaram assim por duas semanas (corrigido em 16/09); as do Fluxo já usavam o admin client.

**Projetos desconsiderados por empresa** (`company_excluded_projects`, migration `20260916120000`): lançamentos dos projetos listados não entram em nenhum número do Financeiro — DRE, Fluxo, Previsto × Realizado, Comparativos, BI e drilldowns. Cadastro em Mapeamento › Projetos › "Projetos desconsiderados" (qualquer empresa, com ou sem plano custom). A regra é o predicado SQL `entry_excluded_by_company_project(company_id, project_code)`, aplicado como `AND NOT` nas 7 funções que leem `financial_entries` (refresh + `_live` + drilldown da DRE; refresh + `_live` + drilldown + `by_registration` do Fluxo). É keyed pela empresa de **origem** do lançamento e é **aditivo**: tabela vazia = comportamento idêntico ao anterior, comprovado por diff zero dos agregados de todas as empresas antes/depois. Os lançamentos nunca saem de `financial_entries`; a API recalcula os agregados ao marcar/desmarcar, então o efeito é imediato e reversível sem re-sync. **Não confunda com a regra da Feat** (`dre_exclude_linked_projects` + `dre_entry_excluded_by_project`): aquela é tudo-ou-nada por empresa, só na DRE, e ficou intocada. Ao criar uma função nova que leia `financial_entries` para número de tela, inclua o predicado — senão o projeto desconsiderado reaparece só ali. O predicado é `SECURITY DEFINER` liberado a `authenticated` de propósito (mesmo enquadramento de `user_has_company_access()`): roda dentro de funções `SECURITY INVOKER` e, sob a RLS do usuário, um lançamento roteado de empresa que ele não vê seria excluído para o admin e incluído para ele.

## Core Business Logic

### Financial Processor (11 Rules) — `src/lib/omie/financial-processor.ts`

Transforms raw Omie API data (ListarMovimentos) into `financial_entries`. Key decisions:
1. Period derived from `dDtPagamento` (cash basis accounting)
2. Apportionment detected when `cCodCateg1..5` are filled — uses `nDistrValor` per portion
3. Non-apportioned entries use `nValPago` or `nValLiquido`
4. BAXP/BAXR origins excluded
5. Entries grouped by period + category, then mapped via `category_mappings` table to DRE accounts
6. Processing decisions logged for audit

### DRE Calculation — `src/lib/dashboard/dre.ts`

- Aggregates `financial_entries` by `dre_account_id`
- Handles hierarchical parent/child account relationships
- Evaluates formulas for calculated accounts (`type = calculado`, `is_summary = true`)
- Computes percentages relative to net revenue (line 1 account)
- Period types: mensal, trimestral, semestral, anual, acumulado
- View modes: simples (single period), comparativa (side-by-side)

### KPI Calculation — `src/lib/kpi/calc.ts`

- Formula types: value, percentage, ratio
- Evaluation: `(numerator / denominator) * multiply_by`
- Zero denominator returns 0
- Ranking uses median across companies over 6-month rolling windows

### CTRL Requisition Workflow — `src/lib/ctrl/actions/requests.ts`

Purchase requests move through a status machine driven by a **budget check** against the sector's annual balance:
- Within budget → `pendente` (manager approval) → `pendente_diretor`? → `aprovado`
- Over budget → requires manager **and** director
- Side states: `aguardando_complementacao` (info requested), `aguardando_aprovacao_fornecedor`, `rejeitado`
Approval tier is computed from remaining annual balance at request time. Once `aprovado`, a request can be launched into Omie *contas a pagar* via `contapagar-launch.ts`. Guard every action with `requireCtrlRole(...)`.

### Vencimento das requisições (Compras)

Duas regras, ambas com fonte única:

- **Cutoff de meio-dia** (`src/lib/ctrl/business-days.ts`): requisição cadastrada até 12:00:00 de Brasília pode vencer no mesmo dia; depois disso, só a partir do **próximo dia útil** (fim de semana e feriado bancário nacional, incluindo os móveis derivados da Páscoa). O formulário usa `earliestDueDateBRT()` no `min` do campo e o servidor repete a trava em `createRequest` — o `min` do HTML é ignorado por alguns webviews. Não recrie um cálculo de cutoff local na tela: existia um em `nova-requisicao-form.tsx` (só "amanhã", sem dia útil) e foi removido em favor do módulo compartilhado.
- **Cartão de crédito vence no dia da fatura da empresa pagadora** (`ctrl_company_omie_config.cartao_dia_vencimento`, cadastrado em Mapeamento Omie). Aplicado no envio ao Omie (`contapagar-launch.ts`, `cardDueDateIso`): à vista aplica a regra de fechamento (compra a partir do dia 23 → fatura +2 meses, senão +1) e o dia é limitado ao último dia do mês; parcelas já vêm com o mês certo da criação e só recebem o dia. Sem dia cadastrado, nada muda (parcelas no dia 05).

### Case — projeto Omie = Fundo do cliente

Todo título de um contrato de show (a pagar e a receber) vai para a Omie com `codigo_projeto` = projeto cujo nome é o **Fundo / Razão social do cliente** (`case_clients.name`). `ensureProjetoByNome` (`src/lib/omie/contapagar.ts`) reaproveita o homônimo (nome normalizado, sem acento/caixa; ativo antes de inativo) e só cria quando não existe — com o nome cortado nos 70 caracteres da Omie **antes** da busca, senão nome longo nunca casaria e cada lançamento criaria um projeto novo. Falha ao resolver o projeto **bloqueia** o lançamento (título sem projeto teria de ser corrigido à mão). Títulos lançados antes desta regra ficaram sem projeto. O BV artístico não usa (não tem cliente).

A **observação de cada conta a RECEBER** descreve o contrato inteiro (`buildObservacaoReceber`, `src/lib/case/observacao-omie.ts`, puro e testado): nº do contrato, fundo, evento/data/local e atrações (obrigatórios, pedido do dono do projeto), cronograma de recebimento, pagamentos por atração/fornecedor, comissões e o BV Case (recebido − saídas, mesma conta do `lancarBvContract`; omitido se não há saída nenhuma). É uma **fotografia do momento do lançamento**: saída cadastrada depois não atualiza a observação já enviada. O a pagar mantém a observação curta. **A Omie apaga o travessão (—) e mostra quebra de linha como `|`** (visto no 1º lançamento real, 29/09/2026): só hífen comum no texto, e uma informação por linha.

### Case — contratante do PDF diferente do cadastro

`case_contracts.pdf_cliente` (jsonb, migration `20260929120000`): quando preenchido, o PDF do contrato mostra ESSES dados do contratante (fundo, doc, responsável, CPF, endereço, cidade, CEP) em vez do cadastro do cliente. `NULL` = mesmos dados do cadastro (a caixa "Usar os mesmos dados" marcada no formulário). **Quem assina na ClickSign segue esses dados** (responsável legal + CPF + e-mail do bloco do PDF, decisão de 29/09/2026), e a validação de assinatura (`signature-check.ts`) roda sobre eles. Omie, projeto e observação do a receber continuam lendo `case_clients`. Os dados próprios substituem o cadastro **por inteiro** (`pdfClienteData` em `src/lib/case/pdf-cliente.ts`, puro e testado): campo em branco sai em branco, senão o PDF juntaria o nome de um contratante com o CNPJ de outro.

### Case — BV artístico (`kind = 'bv_artistico'`)

Segunda modalidade de `case_contracts` (coluna `kind`, migration `20260917180000`): comissão que a Case recebe **do artista que indicou**. Não tem cliente, contrato de venda, ClickSign, aprovação nem conta a pagar — o **único efeito no Omie é uma conta a RECEBER** contra o cadastro do artista, categoria de serviços/BV (`codigo_categoria_servicos`), com o contrato anexado ao primeiro título. Por isso `client_id` virou nulo, com CHECK por tipo: show exige cliente, BV exige `band_id`.

O valor da comissão é **digitado** — o contrato que se anexa é o do artista com o contratante dele e quase nunca traz esse número; o OCR (`extractArtistContract`) serve só para identificar o artista e já seleciona o cadastro quando o CNPJ bate. A comissão vai em `valor_servicos`/`valor_margem`, com os valores de show zerados.

Código próprio, para não torcer o caminho do show: `src/lib/case/actions/bv.ts` (`salvarBvArtistico`, `lancarBvArtistico`), `getBvDetail` em `queries.ts`, `bv-artistico-form.tsx` e `bv-workspace.tsx`. A tela de contrato novo alterna as duas modalidades por `?tipo=bv`, e a lista marca o BV com etiqueta. **Não reaproveite `launchContractToOmie` para o BV**: ela exige cliente, atrações e categorias de custódia/pagar que o BV não tem.

### Case — pedido colado do WhatsApp (`extractContractFromText`)

A tela de contrato novo aceita **colar o pedido como ele chegou** (WhatsApp, e-mail, áudio transcrito) e sugere o preenchimento: `src/lib/case/actions/ocr.ts` interpreta o texto com o provedor de IA ativo (mesmo motor da leitura de contrato, sem visão) e a tela **só preenche campo vazio** — leitura é sugestão, o que o usuário digitou nunca é sobrescrito, e nada é gravado. Cliente com CNPJ (ou nome exato) já cadastrado é **selecionado**, não duplicado. Regras que moram no prompt (`regrasBriefing`): data sem ano vira a próxima ocorrência a partir de hoje; "8k"/"8 mil" viram 8000; parcela "na assinatura/no ato/na reserva" usa amanhã (mesma regra do OCR); e o valor extraído é o **cobrado do cliente** — mensagem que também cita o cachê pago ao artista não pode trocar um pelo outro.

### Case — aprovação antes da ClickSign (`src/lib/case/actions/stages.ts`)

Nenhum contrato vai à ClickSign sem o aval de **um dos aprovadores** (`CASE_CONTRACT_APPROVER_EMAILS` em `contract-config.ts`, hoje Pedro e Marcelo — regra nominal registrada em `user-exceptions.ts`; todos recebem o e-mail e veem o contador no menu). **Aprovar não é assinar**: quem assina pela CS Agência continua sendo só o `CONTRATADO_SIGNER`, por último. Fluxo: `rascunho` → `enviarParaAprovacao` → `aguardando_aprovacao` (e-mail ao aprovador via Resend + contador no item Contratos do menu + faixa na lista) → `aprovarContrato` → `aguardando_assinatura` → `assinado` (webhook). `devolverContrato` volta para `rascunho` e manda o motivo por e-mail a quem pediu (`approval_requested_by`). Se o próprio aprovador clica em enviar, aprova e envia direto.

- **Ordem na ClickSign**: cliente + testemunha no grupo 1, contratado (o `CONTRATADO_SIGNER`) no grupo 2 — ele assina por último. A aprovação **não** é o papel "approve" da ClickSign: a mesma pessoa em dois papéis no documento assina tudo de uma vez, o que quebraria a ordem.
- `prepareForSignature` roda na solicitação **e** na aprovação: valida o cadastro de quem assina (`signature-check.ts` — responsável legal pessoa física, CPF válido, e-mail; o formulário repete a trava antes de salvar), regenera títulos e PDF. Editar os dados (`salvarCliente`) de um contrato em aprovação o devolve a `rascunho`.
- Falha de e-mail não derruba a ação: a pendência continua no menu e na lista.

### Orçamento — Planejamento dos gestores (refeito em 23/09/2026)

O método foi reconstruído do zero. O caminho é **filtrar setores → escolher a categoria → montar**, e a montagem tem três blocos com donos diferentes: a **base** (admin), a **entrevista** (gestor + IA) e as **despesas** (o orçamento), com a **prévia do setor** embaixo se preenchendo a cada despesa confirmada.

- **A despesa virou LINHA de tabela** (`orcamento_planejamento_despesas`). Antes vivia dentro do jsonb `orcamento_planejamento_socios.proposta`, e era por isso que cancelar significava mexer no objeto (`itemPropostaAtivo`) e a trava da diretoria teve de morar na linha pai (migration `20260924120000`). Agora cada despesa tem id, `cancelado` e `diretoria_travado` próprios. **Não existe mais "proposta confirmada"**: a despesa entra na Prévia assim que o gestor confirma o cartão.
- **A IA propõe, o gestor grava.** Quando a IA fecha os dados de uma despesa, ela emite `[[DESPESA]]{json}[[/DESPESA]]` no fim da mensagem; a tela transforma isso num formulário editável e só o clique cria a linha. O parser (`extrairCartaoDespesa`/`parseCartaoDespesa`, puro e testado) roda sobre texto **parcial** do streaming — bloco incompleto não vira cartão, e o texto é cortado no primeiro `[[` para nenhum marcador piscar na tela. `[[FECHAR]]` continua sendo o sinal de fim.
- **A conversa é por categoria × SETOR** (`orcamento_planejamento_entrevistas`, índice único com `COALESCE(setor_id, …)` — setor nulo é valor legítimo). O **card da lista é por categoria**, então a mesma "Marketing" aparece uma vez somando os setores marcados; o setor de cada despesa é escolhido dentro da montagem. Uma conversa só por categoria faria dois gestores escreverem um por cima do outro.
- **A base é do ADMIN e só tem nome + valor pago no ano** (`orcamento_planejamento_base`). É **história, não orçamento**: por isso não tem periodicidade nem mês. Semeada da Omie **agrupada por fornecedor** (lançamento a lançamento daria centenas de linhas numa categoria como Marketing). Reexecutar a semeadura é seguro: casa por **fornecedor**, preserva a curadoria e não ressugere o que foi desconsiderado.
- **Grupos de despesa** são o subnível entre a categoria e a despesa (`PreviaFonteItem.grupo` na Prévia). **Não confundir com `ctrl_expense_types`** (os "Tipos de despesa" do Compras): cadastros distintos, por decisão explícita. A ordenação (alfabética pt-BR, "Sem grupo" **por último**, nunca na letra S) mora em `src/lib/orcamento/grupos.ts` e é compartilhada pelas telas — se cada uma ordenasse por conta, o mesmo orçamento pareceria dois.
- **O grupo é um NOME por empresa + um ESCOPO** (`orcamento_grupos_despesa` + `orcamento_grupo_escopo`, migration `20260927120000`). O cadastro é uma **árvore setor → categoria → grupos**, em **Configuração da empresa** (`config/grupos-despesa`), com empresa e ano vindos da rota. Ela passou um dia nas Configurações gerais, com a empresa como filtro dentro da tela, e voltou em 25/09/2026: grupo **é** por empresa, e contexto fixo separa melhor do que filtro. A conveniência que se perdeu — montar várias empresas sem trocar de tela — virou o botão **"Copiar de outra empresa"**, que é o que de fato se queria. **Não ponha `setor_id`/`category_code` no próprio grupo** — duas coisas quebram: o índice único de nome por empresa barra "Publicidade" existindo em dois setores, e a Prévia agrupa por `grupo_id`, então dois ids homônimos viram dois subníveis lado a lado em vez de **compilar**, que é o comportamento pedido ao olhar vários setores juntos. Reaproveitar o mesmo registro é o que faz o grupo somar como um só.
- **TODO setor recebe TODAS as categorias de despesa** na árvore — sem filtrar por método nem pela atribuição `orcamento_categoria_setores`. Os dois filtros existiram e foram tirados em 24/09/2026 a pedido do dono do projeto: cadastrar grupo é trabalho de estrutura, feito ANTES de se decidir o método e a distribuição por setor, e a árvore incompleta obrigava a voltar ali a cada categoria que mudasse de método ou ganhasse um setor. Consequência: a árvore é longa, e por isso a tela tem **busca** (por nome, código ou nome de grupo) e o recorte "só as que já têm grupos" — **não remova achando que é enfeite**. Cada categoria mostra o método como etiqueta: só `planejamento_socios` usa grupo hoje, e sem o rótulo o admin cadastraria grupos que nunca chegam à entrevista.
- **Copiar os grupos de outra empresa** (`copiarGruposDeEmpresa`) traz a ESTRUTURA, não os registros: o grupo é um nome por empresa, então o destino ganha os seus, reaproveitando os que já tiver com o mesmo nome. O casamento entre empresas é por **nome do setor** e **código da categoria**, e reusa `resolverGrupos` — o mesmo resolvedor testado da importação por planilha, porque o problema é idêntico (nomes de um lado, cadastro do outro). Setor ou categoria que não existe no destino vira um aviso, não um erro do lote, e o mesmo aviso não se repete por escopo. Aditiva e idempotente, como a planilha. O seletor só oferece empresas que **têm** grupos no ano.
- **Os grupos entram por planilha** (`Setor | Categoria | Grupo`), no mesmo padrão do Plano de Cargos: `grupos-xlsx.ts` (puro e testado) + `/api/orcamento/grupos/template` e `/import`. O **modelo já vem com a grade de setores × categorias da empresa preenchida** (e os escopos que já existem) — modelo em branco obrigaria a copiar nomes à mão, e é daí que vem o erro de digitação que faz a linha não casar. A importação é **aditiva e idempotente**: reimportar não duplica (ver a gravação do escopo, abaixo) e nada que esteja no banco e fora da planilha é apagado — remover é ato explícito na árvore. Falha **por linha**, nunca pelo arquivo: setor errado no meio de 200 linhas não impede as 199 certas, e as recusadas voltam com o número da linha. **Setor vazio não é erro** — é o escopo amplo (`setor_id` nulo). Categoria casa por nome **ou** código (a 2ª aba do modelo lista os códigos).
- **Gravar escopo de grupo é SEMPRE via `inserirEscoposFaltantes`** (`grupo-escopo.ts`, puro e testado). **Não use `upsert({ ignoreDuplicates: true })` em `orcamento_grupo_escopo`** — ele não ignora nada ali, por duas razões independentes: a tabela **não tem primary key** (e o PostgREST, sem `on_conflict`, usa a PK como alvo do `ON CONFLICT`), e a chave é um **índice por expressão** (`COALESCE(setor_id, …)`, porque setor nulo é valor legítimo), que `ON CONFLICT (colunas)` não casa nem se o alvo fosse passado. O resultado era 23505 derrubando o lote INTEIRO. Isso quebrava as três telas do mesmo jeito e de forma enganosa: **funcionava na primeira vez** (destino vazio) e nunca mais — "Replicar nos outros setores", "Copiar de outra empresa" e a reimportação de planilha. Pior: como o lote passa a incluir o que já existia, o item NOVO morria junto, e a tela só dizia que o botão não fazia nada. A dedupe agora é por leitura (busca o escopo da empresa × ano e insere a diferença), e os contadores devolvem quantas linhas entraram DE FATO, não o tamanho do lote. Reportado em 29/09/2026 e reproduzido contra produção antes da correção.
- **Escopo vazio = grupo vale em todo lugar.** É o que torna o escopo aditivo: o que já estava cadastrado continua aparecendo até alguém restringi-lo. A regra é `gruposDisponiveis()` em `grupos.ts` (pura e testada), usada pela tela de montagem e pelo prompt da entrevista — oferecer o catálogo inteiro fazia a IA sugerir grupo de marketing numa categoria de pró-labore.
- **A prévia do setor reusa `getPreviaOrcamento`** com o filtro de setor que ela já aceita, e mostra **todas** as categorias orçadas do setor (qualquer método), não só a aberta. Não crie uma segunda soma do orçamento: ela divergiria da Prévia no dia em que uma regra mudasse.
- **KPI, impacto, finalidade e prioridade NÃO têm coluna** — e isso é decisão, não esquecimento. A IA faz essas perguntas para **instigar a reflexão** de quem orça; a resposta é o raciocínio do gestor e fica no transcript, junto com a pergunta que o provocou. Virar campo transformaria a entrevista no formulário que ela veio substituir. O que a diretoria lê é a **justificativa do conjunto**, escrita pela IA no modo `fechamento`.
- **O cartão FECHA a despesa, não a abre** (correção de 24/09/2026). A regra dizia "quando tiver nome, valor, periodicidade e mês, emita o cartão", e isso fazia da COMPLETUDE DOS DADOS o gatilho: gestor que chegava com tudo pronto ("mídia paga, R$ 5.000/mês, de janeiro") pulava a entrevista inteira, e a segunda despesa entrava sem uma única pergunta. Agora ter os dados é condição mínima, não autorização: despesa NOVA exige finalidade + pelo menos uma pergunta de reflexão respondida antes do cartão. A válvula de proporcionalidade continua — item da base em `[conferência rápida]` segue curto, e despesa nova pequena leva uma pergunta, não quatro. Há teste travando os dois lados.
- **Quatro regras da entrevista que vieram de teste real (24/09/2026)**: (a) *a IA tem de saber o que o gestor fez com o cartão* — confirmar e descartar eram cliques só do cliente, então a conversa ficava parada e ela nunca puxava a próxima despesa; hoje `planejamento-entrevista.tsx` manda um turno automático ("Adicionei ao orçamento: …" / "Descartei a sugestão de …") e o prompt obriga a **perguntar qual é a próxima**. (b) *Valor que muda no meio do ano são DUAS despesas*: o cartão tem um valor só e não sabe representar reajuste — "R$ 50 de jan a mai, R$ 60 depois" vira dois cartões com `mesFim`/`mesInicio` encaixados (sem buraco nem sobreposição, com o período no nome), e há teste no motor provando o encaixe. (c) *Duplicidade é dúvida, nunca bloqueio*: a IA compara com a base e com o que já foi registrado e pergunta em três casos — mesmo nome escrito diferente (typo/abreviação), mesma finalidade com ferramentas diferentes, mesmo período com valores diferentes —, mas **se o gestor mantiver, registra e segue**; quem barra é a validação, não ela. (d) *"Para que serve / qual o objetivo" é obrigatória em TODA despesa*, inclusive nas de `[conferência rápida]` — é a resposta que deixa a IA enxergar duas despesas servindo ao mesmo fim.
- **A prévia do setor conta SÓ AS FOLHAS** (`linha.hasChildren || linha.isCalculado` → pula). `coletarFontes`, em `previa-orcamento.ts`, acumula as fontes dos filhos em cada linha-resumo de propósito (para o drilldown de um grupo da DRE mostrar o que há embaixo) — varrer todas as linhas conta a MESMA despesa na folha, no pai e no avô, e o total do setor sai multiplicado pela profundidade da árvore. Apareceu em teste como "Marketing" três vezes.
- **"Todos os setores" no quadro de pessoal vem em BLOCOS, um por setor** (`agruparPorSetor` em `setor-filtro.ts`, puro e testado; vale para as duas abas, Quadro e Benefícios). O consolidado já existia, mas renderizava uma lista corrida — ver todo mundo numa tela só é metade do pedido, porque sem a separação nada diz de quem é cada linha. "Sem setor" vai por ÚLTIMO (mesma convenção do "Sem grupo"), e setor que saiu do cadastro mantém as linhas visíveis em vez de descartá-las — sumir com elas faria o consolidado mostrar menos gente do que existe, sem avisar. O `colSpan` do cabeçalho de cada bloco depende da coluna Empresa, que é condicional.
- **Cancelado/travado pela diretoria tem caminho de volta, e é do ADMIN** (`reativarColaborador`, em `actions/pessoal.ts`; botão âmbar na linha do quadro). Com a validação fora do sistema, quem tinha cancelamento gravado ficava com a linha riscada e sem saída pela tela — e o `[&_button]:pointer-events-none` do bloqueio matava até a lixeira, então nem excluir dava. Hoje os botões nunca são travados e os campos só travam para quem **não** é admin.
- **Desconsiderar uma linha da base OCULTA** (não risca). A linha continua gravada — é o que impede a semeadura de ressugeri-la —, mas some da lista; o admin reexibe pelo contador no cabeçalho para desfazer. O gestor **nunca** vê a desconsiderada: para ele ela não faz parte da base, e mostrá-la riscada só levantaria "por que isso sumiu?".
### Orçamento — categorias irmãs "(*)" são UMA só na construção (25/09/2026)

"Marketing" e "Marketing (*)" são duas categorias da Omie; a divisão é interna à contabilidade e só importa em outras etapas. **Na construção do orçamento é tudo Marketing.**

- A regra é `unificarGemeas()` em `planejamento-calc.ts` (pura e testada): a canônica absorve as `(*)` de mesmo nome e passa a carregar **`codigos`** — todos os códigos da Omie que ela representa. **Use `codigos`, nunca `categoryCode`, para buscar realizado.** `(*)` órfã (sem canônica) é mantida: ali ela É a categoria.
- A unificação acontece na FONTE (`listarCategoriasDespesa`, em `categoria-metodo.ts`), então vale para as telas de montagem de uma vez. Antes existia só no Planejamento (`codigosIrmaos`) e **a Média perdia o realizado da gêmea em silêncio** — era o sintoma que revelou o problema. `codigosIrmaos`/`apenasCanonicas` continuam existindo, mas não recalcule com eles sobre `cats.items`: a gêmea já foi filtrada de lá.
- A comparação de nomes ignora **acento** além de caixa. É seguro porque só uma `(*)` se anexa a uma canônica — duas canônicas nunca se fundem.
- **Dois gates, uma listagem**: `getCategoriaMetodo` (admin, para a tela de configuração) e `getCategoriasOrcamento` (qualquer usuário do módulo que alcance a empresa, para média/valor fixo/planejamento). Separados porque as telas de montagem são do GESTOR e chamavam a versão admin — um gestor tomaria "Acesso restrito" sem motivo; não aparecia porque o Planejamento ainda está escondido dele.
- Gêmea que tinha **método próprio salvo** de antes da regra para de contar (senão dobra) e vira aviso na Prévia (`planejamentoGemeaIgnorada`). Nada é apagado no banco.

- **As provocações ficaram mais afiadas em 29/09/2026, sem tirar nada** (pedido do dono: "não tire nada dele, mas quero deixar ele bem inteligente"). As quatro perguntas — finalidade, necessidade, **KPI**, **impacto em N-1 × projeção em N** e **outros orçamentos** — já existiam; o que faltava era elas dispararem e não aceitarem resposta vaga. Três mudanças: (a) cada provocação agora diz **o que conta como RESPOSTA BOA** e o que reperguntar quando vier genérica; (b) a pergunta de impacto **ancora no número** que o prompt já carrega ("esses R$ X em N-1 renderam o quê?" faz pensar, "qual foi o impacto?" no ar não faz); (c) **a barra sobe com o tamanho** — item pequeno/`[conferência rápida]` segue só com a finalidade, item de peso exige duas provocações respondidas além dela. "Respondida" ≠ "perguntada": uma repergunta no máximo, depois registra e segue. **"Sem indicador" é resposta aceitável** — despesa sem KPI é fato útil para a diretoria, e insistir empurraria o gestor a inventar um.
- **A IA PERGUNTA, não julga** — e este guarda-corpo é o que protege a reversão de 09/09/2026, quando a rodada de "IA analítica" foi desfeita por ela comentar e criticar o CONJUNTO do orçamento (ver a memória `project-orcamento-ia-entrevista-simples`). O prompt proíbe explicitamente veredito sobre o conjunto, rótulo de item irrisório/exagerado/concentrado e proposta de corte por conta própria. Ao enriquecer o prompt de novo, mantenha a linha: **provocação é pergunta; avaliação é de quem valida depois**.
- **O prompt continua base zero** (`entrevista-prompt.ts`, puro e testado) e mantém o que funcionava: materialidade (Pareto — itens que somam 80%, qualquer um com ≥10%, todos quando há até 3; a cauda vai em conferência rápida), classe da despesa (estrutural/contratual/discricionária/variável), `CATEGORIA_DESCRICOES` com regra por categoria prevalecendo sobre tudo, e o mês a mês do ano anterior com os meses fora da curva. `materialidade()` passou a receber **totais**, não itens — a base não tem mais periodicidade.
- **Ditado por voz na entrevista (29/09/2026)**: o microfone ao lado da caixa de resposta (`botao-ditado.tsx`) grava no navegador e manda para `/api/orcamento/planejamento/transcrever`, que chama a OpenAI (`gpt-4o-mini-transcribe`, sucessor do Whisper) **sempre**, qualquer que seja o provedor ativo — Gemini/DeepSeek não transcrevem. O texto **preenche a caixa e não é enviado**: o gestor confere antes, porque um valor mal ouvido iria direto para o cartão. Nada é gravado (nem áudio, nem texto fora do transcript). Regras puras e testadas em `src/lib/ai/transcricao.ts`: a extensão do arquivo sai do mime (a OpenAI identifica o formato pelo NOME; Safari grava mp4), teto de 5 min / 4 MB (limite de corpo da Vercel), e categoria + grupos vão como vocabulário no `prompt`. O consumo entra em `ai_usage_log` no módulo `orcamento`.

O método é justamente o feito para o gestor preencher, e o Gerente Sócio não conseguia nem ver a caixa. O que saiu foi a trava do MÉTODO; o recorte por setor continua valendo. O mecanismo fica de pé para o próximo método em prova — pôr a chave lá esconde a caixa do hub e redireciona as rotas, e é o único lugar (hub, lista e montagem leem de lá).
- As colunas `cancelado`, `cancelado_motivo` e `diretoria_travado` existem na despesa e **ninguém escreve nelas**. `diretoria_travado` seguiu sem leitor mesmo depois da validação voltar: a trava de lá deriva do status, de propósito (ver a seção da validação). A Prévia continua filtrando `cancelado = false`. **Não recrie a marcação em jsonb** que existia antes.

### Orçamento — VALIDAÇÃO da diretoria, versão simples (25/09/2026)

Reconstrução do que saiu em 24/09, com a complexidade cortada de propósito. A semântica inteira cabe em **quatro estados e duas perguntas** — *o item entra no número?* e *o gestor pode editá-lo?* — e mora num módulo puro e testado, `src/lib/orcamento/validacao-diretoria.ts`:

| estado | no número | gestor edita |
|---|---|---|
| `pendente` (sem decisão) | não | **sim** |
| `aprovado` | **sim** | não |
| `reprovado` | não | não |
| `revisar` | não | **sim** (é o único estado em que ele mexe, e vem com o comentário) |

- **Onde se valida**: na **prévia do SETOR**, a mesma faixa que já existia embaixo da entrevista do Planejamento. Três botões por item — ✓ aprovar, ✗ reprovar, 💬 revisar — e um ↩ que desfaz. Ela é compartilhada (`planejamento-previa-setor.tsx` + `validacao-setor-painel.tsx`) e aparece nas telas de **Média**, **Valor fixo**, **Pessoal** (abaixo do quadro) e na montagem do Planejamento. Como ela lista **todas** as categorias orçadas do setor de qualquer método, abrir por qualquer porta dá a mesma lista: o diretor percorre as linhas que o gestor montou, e **não** existe tela consolidada à parte — uma dessas existiu no modelo antigo e foi removida por duplicar a Prévia.
- **No PESSOAL a decisão é na PRÓPRIA LINHA do colaborador** (29/09/2026), com a prévia do setor logo abaixo do quadro. Havia uma aba "Validação" separada e ela SAIU: decidir num lugar e ver o efeito noutro obrigava a trocar de aba a cada ✓. A linha mostra os três botões para quem decide e só a marca do estado para quem não decide — é como o gestor descobre por que a linha travou, em vez de digitar e levar erro ao salvar. A trava passou a DERIVAR da decisão (`colab.travado`), não da coluna morta `diretoria_travado`.
- **A aba "Benefícios" (tela de Pessoal) é admin-only** desde 29/09/2026. O check "Agrupar" dentro dela já era; a aba inteira passou a ser, pelo mesmo enquadramento do regime de apuração: quanto vale o vale-transporte da empresa é premissa, não construção. O botão da aba some E a renderização cai no Quadro para quem não é admin — esconder o botão não é a única defesa. O texto da tela dizia "o admin pré-preenche e o gestor ajusta" e foi corrigido junto.
- **O Plano de Cargos define SALÁRIO e BENEFÍCIOS** (migration `20260929140000`, 29/09/2026). As 7 colunas de benefício foram espelhadas 1:1 em `orcamento_cargo_niveis` (mesmos nomes de `orcamento_pessoal_colaboradores` e de `beneficios.ts`), no **nível**, junto do salário — não no cargo: é onde o dinheiro do plano já mora, benefício que varia por senioridade tem como ser expresso, e no cargo haveria um SEGUNDO lugar de onde a escolha teria de juntar duas fontes. A regra da cópia é `cargo-beneficios.ts` (puro e testado) e tem duas metades, as duas pedidas:
  - **O que o plano DEFINE sobrescreve**, como já acontece com o salário. Senão o plano valeria só para quem entra no quadro pela primeira vez, e mudar alguém de nível deixaria para trás o benefício do nível antigo, em silêncio.
  - **O que o plano NÃO define preserva** — e é daí que vem a regra do pedido: célula vazia no plano = o valor continua vindo da aba **Benefícios**, digitado pessoa a pessoa. Zerar ali apagaria cadastro que ninguém mandou apagar.
  - Por isso **`NULL` e `0` precisam continuar distintos** no banco: `0` é "não recebe" (e sobrescreve), `NULL` é "o plano não diz" (e preserva). Conflar os dois apaga cadastro no gesto mais comum da tela. Há teste travando os dois lados.
  - O valor é **COPIADO, não referenciado** — `orcamento_pessoal_colaboradores` guarda um retrato, igual ao salário: editar o plano em novembro não mexe em quem já está no quadro. Um "fallback vivo" (célula vazia que busca do plano na hora de calcular) foi descartado de propósito: seria uma célula que parece vazia e produz número.
  - No quadro, a escolha do cargo grava por **dois caminhos**: o salário vai no `commit` da linha, os benefícios em `updateColaboradorBeneficios` (a parte verde não passa pelo upsert do quadro) — que já tem trilha e a trava da diretoria. Só grava quando há o que mudar, e a tela recebe um **patch local** em vez de refetch: recarregar ali correria com o `commit` que ainda está gravando e poderia reverter a célula.
  - **O `select` do nível é string literal** (`NIVEL_COLS`), porque o client tipado do Supabase analisa o select em tempo de compilação e não entende template literal. Esquecer um benefício ali não quebra nada — o valor do plano só nunca chega ao colaborador, em silêncio. Quem cobra é `cargo-beneficios.test.ts`, que lê a constante.
  - **A leitura degrada sozinha enquanto a migration não roda**: `lerNiveis` (em `cargos.ts`) e o setup do Pessoal caem na lista sem benefícios ao levar 42703, em vez de derrubar a tela inteira por causa de um recurso acessório. A GRAVAÇÃO não tem como degradar — `friendlyCargoError` nomeia a migration que falta.
  - **`applyReajuste` não alcança benefício** (o upsert lista só as colunas de salário, e `ON CONFLICT DO UPDATE` só toca nelas): dissídio é de salário, vale-transporte não sobe junto. **`cloneCargos` leva os benefícios**, senão o ano novo nasceria com salário e sem pacote. **A importação por planilha continua só de salário** — nível novo entra com benefício nulo e nível existente conserva o que tinha; não é esquecimento, a planilha é ferramenta de salário.
- **O seletor "Regime de apuração" (tela de Pessoal) é admin-only na TELA**, não só na action. `setRegimeApuracao` já recusava quem não é admin, então o seletor à vista era um controle que só levava a uma recusa — e ele muda o número da empresa inteira (o 13º cai em nov/dez no caixa e 1/12 na competência). É premissa, do mesmo naipe do plano de cargos e dos encargos: o gestor monta o quadro, não redefine o regime.
- **LER encargos NÃO é admin-only** (`getEncargos`/`getEncargosPorEmpresa`) — escrever (`setEncargos`/`resetEncargos`) continua sendo. Era admin nos dois, e isso quebrava o PESSOAL inteiro para gestor: `getPrevia` (o motor da folha) chama `getEncargos`, que devolvia "Acesso restrito a administradores", a prévia do pessoal falhava e as despesas com pessoal **sumiam de toda prévia** — do setor e da empresa. A alíquota não é segredo: é a premissa do número que o próprio gestor monta. No lote (`getEncargosPorEmpresa`) não se exige alcance às OUTRAS empresas citadas no quadro — se exigisse, o número mudaria conforme quem abre a tela.
- **O erro do pessoal SOBE para a tela** (`resumo.pessoalIndisponivel`). `getPreviaOrcamento` engolia o erro de `getPrevia`: a prévia seguia sem a folha, com um total menor e nenhuma explicação — e a folha é quase sempre a maior linha do orçamento. Derrubar a Prévia inteira também não serve (o resto dela está correto), então o motivo vira faixa âmbar na Prévia da empresa e na prévia do setor. **Ao acrescentar um método à Prévia, não repita o padrão de ignorar o erro dele** — número menor sem motivo é o pior resultado possível aqui.
- **A prévia do setor se move NO CLIQUE** (`previa-setor-decisao.ts`, puro e testado). A decisão é aplicada na tela antes do round-trip e o refetch confirma — esperar o servidor fazia o gesto mais repetido da validação parecer travado, e o diretor clicava de novo achando que não tinha pegado. `aplicarDecisao` recalcula o conjunto inteiro (item → grupo → categoria → total do setor → contadores): mexer só no item deixaria a tela internamente inconsistente até o próximo refetch, o que é pior do que não atualizar. Erro do servidor recarrega e desfaz o que foi antecipado. Categoria sem itens (média sem linha gravada) conserva o total do servidor em vez de zerar.
- **No Pessoal a decisão acontece num componente IRMÃO da prévia**, então a linha avisa qual foi (`decisaoExterna` no `ValidacaoSetorPainel`) — sem isso a prévia abaixo ficava parada até sair e voltar da tela. O `seq` é o gatilho, não o conteúdo: aprovar → desfazer → aprovar produz decisões idênticas e as três precisam valer.
- **A trava do gestor DERIVA do status, nunca de coluna.** Não recrie `diretoria_travado`: era escrito e liberado à mão, e foi ele que deixou colaboradores presos sem saída pela tela. As actions chamam `travaDaValidacao(...)`, que devolve a mensagem de recusa ou `null`. Diretoria e admin passam sempre. Tabela ausente não trava nada — a validação não pode ser o motivo de o módulo parar de aceitar escrita (tolerância de desenho; a migration está aplicada desde 28/09/2026).
- **A edição VENCE a decisão** (`decisaoVencida`): a decisão guarda `decidido_em` e qualquer UPDATE empurra o `updated_at` do item para depois dela, devolvendo-o a `pendente`. É o que dispensa hook nas 15 actions de escrita — **caminho de escrita novo já nasce coberto**, e o que alguém esquecer de instrumentar também. Empate conta como decisão válida (artefato de relógio, não edição).
- **Só o aprovado compõe a Prévia da empresa**, e o número se move a cada ✓ — não fica zerado até tudo passar. A Prévia devolve o par (`totalDespesa` × `totalDespesaAprovada`), a tabela troca a série por um botão **Orçado / Aprovado** (que só aparece quando os dois divergem) e uma faixa nomeia o que ficou de fora — total menor sem dizer o que faltou é o tipo de número que leva à decisão errada.
- **O escopo da DECISÃO é a empresa, não os setores do decisor.** `decidirItem`/`limparDecisao` usam `autorizarLeitura`, nunca `autorizarEscrita` — e isso é a pegadinha central: o diretor também **monta** o orçamento do setor dele, e desde que o ciclo saiu `setoresDeEscrita` o trata como construtor comum, restrito aos setores vinculados. Usar o escopo de escrita aqui faria o diretor tomar "só pode alterar os setores vinculados a você" na maioria dos itens que ele precisa verificar. Construir e decidir são alcances diferentes — mesmo enquadramento do Compras, onde o diretor aprova qualquer setor mas só é notificado dos dele. Quando o roteamento por diretor entrar, é aqui que ele recorta.
- **Só o aprovado vai para o BUDGET, nos dois publicadores.** `publicar.ts` (empresa inteira) usa `mesesAprovados` das folhas, e `enviarPreviaParaOrcamento` (a folha — o botão dele na aba Prévia do Pessoal foi **retirado em 29/09/2026** a pedido; a action segue no código, sem tela) soma **pessoa a pessoa** só os aprovados — somar as partes é exato, não rateio. Os dois recusam com a mensagem "nada foi aprovado ainda" em vez de publicar zero em silêncio, distinguem isso de "ninguém orçou" e reportam quanto/quantos ficaram de fora. O `totalAno` que a tela mostra é a soma do que FOI publicado, não o da prévia cheia.
- **A média tem um item por LINHA GRAVADA** (categoria × setor), não um item agregado. Até 25/09/2026 a Prévia somava as parcelas de todos os setores num item só e o ancorava no setor da **maior** parcela: um ✓ valia por vários setores, e editar os outros não era barrado embora continuassem somando no aprovado. E como a média "viva" (sem linha salva) é ancorada em `(categoria, ∅)` enquanto a primeira gravação resolve o setor, `travaDaLinhaDeMedia` confere **as duas chaves** — senão a própria gravação que a decisão deveria barrar a contornaria em silêncio.
- **Somar as partes aprovadas é EXATO, não rateio.** O motor do pessoal roda por colaborador, então a soma dos aprovados reproduz o agregado deles com encargos, férias e 13º certos — um ✓ no colaborador aprova a pessoa inteira. Ratear por proporção erraria: RAT/FAP e o teto do INSS não são lineares no total. O mesmo colaborador aparece em Salários, Encargos e Benefícios com o **mesmo alvo**, então um ✓ marca as três — e por isso todo contador **deduplica por `alvoTipo|alvoId`**, senão a pendência sai triplicada.
- **A Prévia da empresa tem TRÊS leituras**: o botão **Orçado/Aprovado** troca a série da tabela, e **Comparar** abre o mês clicado em quatro colunas — orçado, aprovado, diferença e %. É por clique no cabeçalho porque 12 meses × 4 colunas não cabem na tela. A matemática é pura e testada (`previa-comparativo.ts`): **orçado zero devolve percentual `null`, não 0 nem Infinity** — "não dá para dizer" é diferente de "nada aprovado", e a tela mostra "—".
- **As linhas abrem e fecham como na DRE** (`linhasVisiveis`, testada): fechar um grupo esconde o **ramo inteiro**, netos inclusive, comparando por prefixo de código (`7.` não esconde `70`, que é outra conta). Guarda-se o que está FECHADO, não o que está aberto, para conta nova aparecer por padrão em vez de nascer escondida. **O Excel ignora o abre/fecha** — exportar só o expandido entregaria uma planilha que não soma.
- **O DRILLDOWN segue a visão, e não seguia**: no modo Aprovado ele listava os valores orçados, então o item reprovado aparecia com o valor cheio e o leitor concluía — com razão — que ele estava sendo contado. Os totais da tabela sempre estiveram certos (conferido contra produção em 29/09/2026: 7 aprovadas e 1 reprovada, aprovado R$ 10.676,92 contra orçado R$ 21.426,92). Agora o diálogo usa `mesesAprovados`/`totalAnoAprovado` e **zera o item que não entrou**, mantendo-o listado e riscado: sumir com ele esconderia o que ficou de fora.
- **O Excel da Prévia traz uma 2ª aba "Aprovado"**, e só quando as duas séries divergem. Vai em aba separada em vez de seguir o botão Orçado/Aprovado da tela porque o arquivo na pasta de downloads não diz qual série ele carrega — e a comparação é justamente o que se quer ver. O drilldown de uma linha da DRE mostra o ponto do estado em cada item e o aprovado da origem.
- **A árvore do aprovado roda pelo MESMO motor** (`buildDashboardRows`, segunda passada sobre `leafAprovadoByScopedId`): as fórmulas das linhas calculadas precisam ser avaliadas sobre o subconjunto, não recortadas depois.
- **`alvo_id` é TEXT** porque a **média** é chaveada por `(categoria, setor)` (`chaveMedia`) — a linha dela pode nem existir enquanto o gestor não salva o valor "vivo" do realizado. Os outros três alvos são uuid de linha.
- **Um comentário, não um chat** (pedido explícito). O diretor escreve o que mudar; o gestor responde **editando**, e a edição devolve o item à fila dele. O histórico de quem decidiu o quê é da trilha, que já registra tudo. Aprovar ou reprovar **limpa** o comentário — pedido velho pendurado em item resolvido confunde.
- **A faixa de números da prévia do setor é recortada no MÉTODO da tela** (`metodoContagem`, 29/09/2026), enquanto a LISTA continua sendo o setor inteiro. A lista é assim de propósito (o diretor percorre o mesmo conjunto abrindo por qualquer porta), mas a faixa em cima dela é lida como "o que falta NESTA tela" — e não era isso que ela dizia. Caso real que revelou: no Pessoal ela mostrava **"33 a verificar · 10 aprovadas · 2 reprovadas"** com 10 colaboradores no quadro, 3 aprovados e 1 reprovado; as 10 eram 3 colaboradores + **7 despesas do Planejamento**, e as 2 eram 1 colaborador + 1 do Planejamento (conferido contra produção). **Não era falta de dedupe** — a dedupe por `alvoTipo|alvoId` sempre funcionou, e a diferença entre as 4 aprovações no banco e as 3 na tela era uma decisão **vencida por edição posterior**, que é o comportamento correto.
  - A conta é `contarPorMetodo` (`previa-setor-contagem.ts`, puro e testado) e deriva de `categorias`, a MESMA estrutura que `aplicarDecisao` mantém — assim o número se move no clique junto com os totais, sem um segundo caminho para divergir de `resumo.contagem`.
  - **O texto nomeia o que conta** ("6 colaboradores a verificar", "3 aprovados"): a lista logo abaixo continua com o setor inteiro, então número menor sem dizer do que ele fala é o tipo de número que leva à conclusão errada. `ROTULO_POR_METODO` carrega o gênero porque o particípio concorda — colaboradores **aprovados**, despesas **aprovadas**.
  - Hoje só a tela de **Pessoal** passa a prop. Média, Valor fixo e Planejamento seguem com a contagem do setor inteiro; ligar cada uma é uma linha (`metodoContagem="media"` etc.), e os rótulos já estão no mapa.
- **Contadores no card de cada método** (`contarValidacoesPorMetodo`), recortados pelo setor de quem pergunta: o diretor lê "N a verificar", o gestor "N com pergunta · N aprovadas · N reprovadas". Card sem nada orçado não ganha rodapé.
- **Tabela**: `orcamento_validacoes` (migration `20260928120000`, **aplicada em 28/09/2026**), uma linha por item decidido, única por `(company_id, year, alvo_tipo, alvo_id)` — decidir de novo sobrescreve. Não há fase, rodada, versão congelada, entrega por setor, liberação de item nem pedido de liberação: foi esse conjunto que tornou a validação anterior complexa demais.

### Orçamento — a VALIDAÇÃO e o CICLO foram removidos do sistema (24/09/2026)

**A validação JÁ FOI reconstruída — ver a seção acima (25/09/2026).** O que segue é o registro do que foi TIRADO em 24/09 e continua fora: o CICLO, a trava por fase, o visto linha a linha, a tela de retorno e o gate por campo. Vale como histórico e como o que herdar se algum desses voltar.

**Saiu** (~2.700 linhas): `validacao.ts` (puro) e `actions/validacao.ts` (cancelar / alterar / adicionar item, solicitar ajuste, liberar item, pedir liberação, responder solicitação); `actions/revisao.ts` (o "visto" linha a linha e a finalização da tela por setor); `actions/retorno.ts` e a tela `/retorno` (`retorno-view.tsx`); `barra-validacao.tsx` (`BarraValidacao`, `VistoRevisao`, `BarraFinalizacao`). Junto com eles saiu o **gate por campo** (a diretoria só trocava o índice na média e índice+mês no valor fixo), a **trava por item** (`diretoria_travado`), a trava de **tela finalizada** no pessoal e o contador de pendências no menu (`navBadges` ficou zerado, com a fiação pronta).

**O CICLO saiu junto, numa segunda passada** (~2.000 linhas): `ciclo.ts` + `ciclo.test.ts`, `actions/ciclo.ts`, `notificacoes.ts`, `ciclo-painel.tsx` (o quadro do hub com as transições e as entregas dos setores) e `ciclo-faixa.tsx`. Com ele foi embora a **trava por fase** dentro de `autorizarEscrita`: **o orçamento voltou a ser sempre editável** por quem alcança o setor. O motivo de tirar tudo: o painel era o único caminho para mover o estado, então mantê-lo fora com a trava dentro prenderia em somente leitura, sem saída pela tela, qualquer empresa que já estivesse em `em_validacao`.

`autorizarEscrita` devolve só `{ user, setores }` — sumiram `estado`, `fase` e `cicloId`. **É nele que a trava POR FASE volta** se o ciclo for redesenhado: foi assim que as 15 actions de escrita a ganharam de uma vez, sem mudar nenhuma delas. Não confunda com a trava por ITEM da validação, que já existe e deriva do status (`travaDaValidacao`) — são coisas diferentes e convivem. O selo heurístico de `status.ts` (conta linhas preenchidas) voltou a ser a única leitura de andamento no hub.

**Ficou a TRILHA** (`trilha.ts`, `actions/trilha.ts`, `orcamento_alteracoes`), que segue registrando cada escrita. Duas mudanças nela: `TrilhaFase` passou a ser definida no próprio `trilha.ts` (era do ciclo) e `fase` virou **opcional**, caindo em `FASE_PADRAO` (`'construcao'`) — sem ciclo, toda escrita é construção. Os cinco valores do tipo continuam existindo para as linhas já gravadas seguirem legíveis e para o redesenho voltar a preenchê-los sem migration. `travaOItem` saiu (escrevia `diretoria_travado`, que ninguém lê).

**As colunas e tabelas do banco não foram tocadas**, por decisão do dono do projeto: `diretoria_travado`, `cancelado`, `cancelado_motivo`, `cancelado_por`, `cancelado_em` continuam nas tabelas de método, e as tabelas `orcamento_ciclos`, `orcamento_revisoes`, `orcamento_validacoes_tela`, `orcamento_setor_entregas`, `orcamento_versoes` e `orcamento_versao_linhas` continuam existindo. Ninguém lê nem escreve nelas. É reversível e o redesenho provavelmente quer algo parecido — **não as remova achando que são lixo**.

**Três decisões antigas que vale herdar**: o ciclo tinha **entrega por setor** (cada gestor declarava o seu pronto, e o admin podia enviar para validação mesmo com setor pendente, avisando quais faltavam); a validação acontecia DENTRO das telas de método (o diretor escolhia o setor e percorria as mesmas linhas de quem constrói) porque uma tela consolidada chegou a existir e foi removida por duplicar a Prévia; e cancelar era MARCA, nunca exclusão — a linha ficava visível, riscada e com o motivo, senão o gestor perdia o que escreveu e a trilha virava o único lugar onde aquela despesa existiu.

## Authentication & Authorization

- Supabase Auth with HTTP-only cookies; session refreshed in `src/lib/supabase/middleware.ts`.
- `getSessionContext()` (in `session.ts`) is the single entry point — returns `{ user, profile, modules }`. The `users` row is created by the `on_auth_user_created` trigger on signup; no row → empty session → `/pendente`.
- First user auto-promoted to admin **in dev mode only**.

### Two role models live side by side (mid-migration)

The schema is transitioning from the old flat-role model to a **profile + per-module** model. Both exist; know which you're touching:

- **New model (authoritative for pages)** — `canAccessPathByProfile(pathname, profile, canFinanceiro, canCompras, canCase, canViagens, email)`. `profile` is a `UserProfileType`: `admin`, `franqueado`, `csc`, `validador_contrato`, plus CTRL profiles `solicitante`, `gerente`, `gerente_setor`, `diretor`, `contas_a_pagar`. `csc` ("CSC") is a functional copy of `franqueado` ("Visão Financeira") plus the *Validação Relatório* screen — change one only after deciding whether the other follows. Module access is two booleans (`can_financeiro`, `can_compras`). `defaultLandingFor(...)` decides post-login redirect.
- **Legacy model** — `canAccessPath(pathname, dreRole, ctrlRole)` with `DreRole` (`admin`/`gestor_hero`/`gestor_unidade`) and `CtrlRole`. Still called by older code; tables `DRE_RULES` / `CTRL_RULES` / `SEGMENT_SUB_RULES` back it. Will be removed once all callers migrate.

Session helpers: `hasDreAccess(ctx, minRole?)` (hierarchy `gestor_unidade < gestor_hero < admin`), `hasCtrlAccess(ctx, roles?)`. In CTRL server actions use `requireCtrlRole(...allowed)` / `getCtrlUser()` from `src/lib/ctrl/auth.ts`.

Special profiles to remember:
- `franqueado` — explicit **whitelist** of DRE view screens (dashboard, fluxo-de-caixa, budget-forecast, kpis, business-intelligence, documentos), at both `/...` and `/s/<slug>/...`. Everything else (conexões, mapeamento, configurações, admin, ctrl, contratos, usuarios) is denied.
- `validador_contrato` — island: only `/contratos*`. Continua existindo, mas **não é mais o único caminho** para a tela — ver o módulo Validação de Contratos abaixo.

### Criar um módulo novo: os pontos de fiação

Um módulo (VB, Contratos, Caixa…) só "existe" depois de ~13 arquivos. A lista, em ordem: `src/lib/auth/<modulo>.ts` (constantes + `has<X>Grant`/`set<X>Grant`), `session.ts`, `supabase/types.ts` (`UnifiedProfile` + `ModuleAccess`), `access.ts` (gate de rota + `defaultLandingFor`), `context/active-context.ts`, `context/modules.ts`, `components/app/navigation.ts` (grupo + flag no `NavItem`), `components/app/nav-links.tsx` (regra em `isItemVisible`), `app-shell.tsx`, **os 5 layouts existentes** + o do módulo novo, `users-admin-manager.tsx`, as 3 rotas de `api/users/*`, `usuarios/page.tsx`, `supabase/middleware.ts` e a root `page.tsx`.

**A armadilha**: as flags de módulo são **opcionais** em `BuildInput`, então esquecer uma num dos objetos montados campo a campo **compila limpo** e o item some do menu para todo mundo, sem erro em lugar nenhum — `tsc`, ESLint e build passam, e `visibleNavKeys` (a função exportada e testável) recebe o objeto já pronto, então o teste também passa. Foi assim que o Caixa nasceu invisível. `NavLinks` agora repassa `props` inteiro justamente para fechar esse buraco; o `visibleNavKeys` do `app-shell` continua sendo montado campo a campo (os nomes divergem) — **confira os dois**. E abra a tela: esse defeito só aparece olhando o menu.

### Regras nominais (exceções por usuário fixas no código)

Alguns acordos de negócio não têm campo de cadastro e vivem no código: alçada de aprovação restrita e roteamento fixo (`src/lib/ctrl/routing.ts`), visão completa do Compras (`src/lib/ctrl/full-view.ts`) e a liberação da Validação Relatório (`src/lib/auth/bi-validation.ts`).

`src/lib/auth/user-exceptions.ts` é a **vitrine** dessas regras: não define nada, apenas lê as fontes acima e as descreve em português. A tela de Usuários usa isso em dois lugares — um ícone âmbar na linha de quem tem exceção e o botão "Regras especiais" no cabeçalho, que abre o catálogo completo. O catálogo também aponta **regras órfãs** (e-mail/ID do código que não existe mais na base), que de outro modo deixariam de valer em silêncio.

**Ao criar uma regra nominal nova, registre a leitura dela em `user-exceptions.ts`** — senão ela volta a ser invisível para quem administra os usuários, que é exatamente o problema que essa tela resolve.

### Empresas restritas (Business Intelligence e Documentos anexos)

`src/lib/auth/restricted-companies.ts` lista empresas que só aparecem para quem tem o vínculo explícito em `user_company_access` — e aqui **admin não passa por cima**. Hoje: Dataforte.

Existe porque essas duas telas são de escopo **global**: listam empresas de todos os segmentos numa lista só, sem o filtro por `segment_id` do Dashboard/Fluxo/Budget. Como `resolveAllowedCompanyIds` devolve tudo para `role = 'admin'`, a Dataforte aparecia no seletor das duas telas para os três admins, nenhum deles cadastrado na empresa. A regra de negócio é "só quem está no cadastro vê".

A trava está na tela **e** em toda API que a tela chama (listagem/upload/exclusão/download de documentos, geração do One Page e o histórico dele) — esconder do `<select>` não é a única defesa. O escopo para de propósito nessas duas telas: as telas por segmento seguem com admin vendo tudo, senão Mapeamento, Configurações e o sync da Omie quebram para a empresa restrita.

Para liberar alguém (admin inclusive), marque a empresa na tela de Usuários. É o único caminho, de propósito — a liberação fica num cadastro visível, não numa lista de e-mails no código.

### Módulo Validação de Contratos (`/contratos`)

`src/lib/auth/contratos.ts` é a fonte de verdade. A tela deixou de ser exclusiva do perfil `validador_contrato` (que isolava o usuário) e virou um **módulo** marcável em "Módulos visíveis" na tela de Usuários — assim um Gerente Sócio do Compras, por exemplo, pode validar contratos sem trocar de perfil.

A concessão é gravada numa linha de `user_module_roles` (`module='contratos'`, `role='validador'`), **não** numa coluna `can_contratos` em `users`. Foi decisão consciente: coluna nova exigiria migration, e enquanto ela não roda o `select` explícito de `getSessionContext` quebra inteiro (42703) e derruba o app. A sessão expõe o resultado como `profile.can_contratos`, então o resto do código lê como se fosse mais uma flag de módulo. Quem lê a flag precisa ler a linha: `getSessionContext`, o middleware e a root page (`/`) fazem o mesmo join. `validador_contrato` (e o flag legado `contracts_only`) continua implicando o módulo, então ninguém perde acesso.

As policies de `contract_validation_batches` / `_items` só conhecem `is_admin()` / `is_hero_manager()` — como o módulo agora pode cair em qualquer perfil, as páginas `/contratos` leem com service role (mesmo padrão que `/api/contracts/batches` já usava), depois de checarem `profile.can_contratos`.

O módulo é liberável em **qualquer perfil**, inclusive `franqueado` ("Visão Financeira") e `csc` — que escondiam a seção "Módulos visíveis" inteira por serem só-Financeiro e hoje mostram só esse botão. Duas ordens importam por causa disso: em `canAccessPathByProfile` o gate de `/contratos` vem **antes** do bloco franqueado/CSC (a whitelist deles negaria a rota), e em `nav-links.tsx` o item é decidido **antes** de `FRANQUEADO_NAV_KEYS`/`CSC_NAV_KEYS`. Só `admin` (tem tudo) e `validador_contrato` (é o próprio módulo) seguem sem a seção.

No menu, a tela tem grupo próprio (`CONTRATOS`); saiu de PLATAFORMA, onde convivia com as telas de administração sem ter relação com elas.

"Viagens" saiu de "Módulos visíveis" (módulo sem uso). As colunas `can_viagens`/`can_viagens_aprovar`, o módulo e o kill-switch `VIAGENS_ENABLED` continuam existindo; o formulário só carrega e devolve os valores atuais, sem oferecê-los.

### Módulo VB (`/vb`, Viva Bank)

Controle dos créditos de sócios/credores que emprestaram ao grupo na construção do Terrazzo — substitui a planilha `docs/VB TERRAZZO V2.xlsx`. Desenho: `docs/superpowers/specs/2026-09-09-vb-viva-bank-design.md`.

- **Acesso só por concessão**: linha em `user_module_roles` (`module='vb'`, `role` `gestor` | `credor`), lida por `src/lib/auth/vb.ts`. **Admin não passa por cima** (mesma filosofia das empresas restritas): sem a linha, o grupo VB não aparece no menu e `/vb` redireciona. O gate em `canAccessPathByProfile` vem antes de "Admin: tudo" de propósito. Hoje só o Marcelo tem `gestor`; a tela de Usuários ainda não oferece o botão (fase 2, junto com o papel `credor`, que verá só o próprio extrato via `vb_creditors.user_id`).
  - O perfil `validador_contrato` é ilha (só `/contratos`) e não alcança o VB mesmo com a concessão; qualquer outro perfil, inclusive `franqueado`/`csc`, entra com a linha.
- **Histórico congelado**: cada linha da planilha virou um lançamento com o valor que estava lá (`rate_basis` registra o método: `mensal` = taxa fixa capitalizada por dia, `periodo` = saldo × CDI do período, `ajuste` = valor digitado). O sistema não recalcula juros do passado — os saldos são fatos acordados com cada credor.
- **Saldo nunca é gravado**: é a soma de `vb_entries.amount` (com sinal) em ordem `(entry_date, sort_order, created_at)` — `src/lib/vb/ledger.ts`. Só `status='aprovado'` entra em saldo e totais.
- **Importação com revisão**: `POST /api/vb/import` parseia o `.xlsx` (`src/lib/vb/import/parse-vb-workbook.ts`, função pura) e grava os lançamentos como `pendente` na própria `vb_entries`, num `vb_import_batches` (um pendente por vez). A revisão compara o SALDO da planilha (`sheet_balance`) com o saldo somado; até R$ 1,00 é arredondamento. Aprovar (`vb_approve_import_batch`, transação) exige zero flags bloqueantes (`data_invalida`, `valor_invalido`). Credor com lançamento aprovado nunca é reimportado. `npx tsx scripts/vb-parse-check.ts` confere a planilha real sem tocar o banco.
- **Importação é uma vez só**: não há item de menu; a Visão geral oferece "Importar histórico" enquanto não existe histórico aprovado (nem lote pendente), e a página `/vb/importar` recusa novo upload depois disso — a tela continua acessível por URL, como histórico das importações. Depois da aprovação, tudo é lançamento manual (`Novo lançamento`, na Visão geral ou na tela do credor).
- **Novo lançamento é uma operação com várias linhas**: cabeçalho (data e descrição, iguais para todas) + linhas `credor · tipo · valor`. A faixa "Lançar também para" liga e desliga credores replicando tipo e valor da última linha preenchida — é como se lança o mesmo valor para vários (PLR, juros do mês) digitando uma vez. **Nenhuma linha nasce com credor preenchido** quando o diálogo abre sem credor de contexto (Visão geral): o padrão anterior mandava o lançamento para o primeiro da lista sem ninguém perceber, e isso aconteceu em produção. A composição das linhas é pura e testada em `src/lib/vb/new-entries.ts` (`replicatedFrom`, `toggleCreditorLines`, `addAllActiveLines`), sem obrigar o líquido a fechar em zero (pagar vários credores no mesmo dia não fecha; transferência entre dois fecha). Período e taxa aparecem só quando há linha de rendimento e valem para todas elas ("juros do mês para todos"). As linhas vão num único INSERT (tudo ou nada) e compartilham `vb_entries.group_id` — o vínculo existe no banco, mas o extrato não o exibe. A montagem das linhas é a função pura `src/lib/vb/new-entries.ts` (`buildEntryRows`, com testes); a action `createVbEntries` só confere os credores e grava. Não existe mais lançamento de credor único: é o mesmo formulário com uma linha.
- **Uma tabela só, em formato de extrato bancário**: `src/components/vb/statement-table.tsx` (`VbStatementTable`) desenha tanto o extrato do credor (separador por ano com totais) quanto a revisão do lote (flags e ações por linha) — as opções são props. A cor carrega o tipo (entrada verde, saída vermelha, rendimento azul) e o saldo negativo é vermelho. A conferência saldo-planilha × sistema é feita pelo script `scripts/vb-parse-check.ts` e o banco guarda `sheet_balance`/`source_row` para auditoria, mas **a interface não mostra nenhuma referência à planilha** (pedido do dono do projeto: "a planilha foi só o meio de entrada"). Não crie uma segunda tabela para o VB; a faixa de indicadores das duas telas também é compartilhada (`stat-strip.tsx`). As telas listam do mais recente para o mais antigo (`VbStatementTable` inverte para exibir; o saldo é calculado em ordem cronológica antes da inversão e antes de qualquer filtro). A tela do credor continua server component e entrega os lançamentos ao `statement-view.tsx` (client), que monta faixa, gráfico da evolução do saldo, filtros (ano, tipo, busca) e a tabela.
- **Triagem da Omie (`/vb/omie`, só gestor)**: os pagamentos da ABD Holding (`VB_OMIE_COMPANY_ID`, `src/lib/vb/omie/config.ts`) vêm do sync diário do DRE — a tela lê `financial_entries` (tipo `despesa`, data ≥ `VB_OMIE_START_DATE`) e **não** tem integração própria com a Omie; "Buscar na Omie" só dispara o mesmo `runCompanySyncAsSystem(…, "rolling")` do cron. A decisão por movimento fica em `vb_omie_triage` (chave única `(company_id, omie_id)`, status `vinculado`/`descartado`, com retrato do pagamento porque o sync apaga o que some da Omie); **pendente não é gravado** — é candidato sem decisão. Vincular reaproveita o diálogo multi-linha (`VbEntryDialog` com `omie`): grava os lançamentos com `group_id`, depois a decisão, e apaga os lançamentos se a decisão falhar (`src/lib/vb/actions/omie.ts`). Desvincular apaga o grupo e devolve o movimento — é a única exclusão de lançamento aprovado que existe. Sugestões (`src/lib/vb/omie/suggest.ts`, puro e testado) só propõem credor e tipo. Leituras e escritas desta tela usam o admin client depois do gate de gestor, porque as policies de `financial_entries` dependem de vínculo com a empresa. O contador do menu vem do layout `(vb)` (`navBadges`). O extrato do credor não mostra origem Omie.
- **Rendimento por CDI (`src/lib/vb/cdi/`)**: o saldo parado de cada credor ativo rende 100% do CDI diário do Banco Central (série 12 do SGS), baixado pelo cron `/api/cron/vb-cdi` e guardado em `vb_cdi_rates` — guardar é o que torna o cálculo reproduzível e auditável. **O prazo é de cada credor, não uma data única**: o ponto de partida é o **fim do último rendimento aprovado do credor, de qualquer base** (`accrualStartFor`; credor sem rendimento parte do primeiro lançamento), e dali até a última taxa gravada o motor corta em cada movimentação e rende cada trecho com o saldo que havia. Decisão de 14/09/2026 — antes existia um marco zero global (`VB_CDI_START_DATE`) que fazia todo mundo partir do mesmo dia. **Não use "último lançamento" como partida**: a conferência do mesmo dia mostrou trechos entre o último rendimento e a movimentação seguinte que ficariam sem render (Sotrate 30/06→01/09, Vitor e Maria Ap em julho; R$ 27,9 mil no total). Por isso o `syncCdiRates` também **preenche para trás**: baixa o CDI desde o ponto de partida mais antigo entre os ativos (`earliestAccrualStart`); a constante hoje é só o início padrão do download quando não há credor com lançamento. O botão "Calcular rendimento" existe na Visão geral (todos os ativos) e na tela do credor (só ele, `creditorId` no diálogo) — mesma action, mesmo plano — e tem o campo "Calcular até" (`upTo`, limitado à última taxa). A lógica compartilhada (plano, gravação, reconciliação) mora em `cdi/service.ts`; as actions são só o gate de gestor. **O rendimento nunca atravessa a virada do mês** (`monthEndsBetween` é corte obrigatório no motor, decisão 15/09/2026): assim o extrato mensal sempre traz o rendimento do mês dentro do mês. **O cron do dia 5 (`/api/cron/vb-monthly-reports`) fecha o mês anterior automaticamente** antes de avisar os gestores — é a única gravação de lançamento por cron no VB (uma linha por credor, descrição "Rendimento CDI (fechamento do mês)", `created_by` nulo). **Lançamento retroativo recalcula**: `reconcileCdiAfterChange` (chamado por `createVbEntries`, `linkOmieMovement` e `unlinkOmieMovement`) apaga os rendimentos por CDI cujo período termina depois da data alterada e recalcula até onde o mais tardio deles chegava — como o motor reconstrói a partir da linha do tempo, isso é toda a regra. Os rendimentos importados da planilha (`rate_basis` ≠ 'cdi') nunca são recalculados; data anterior a eles só avisa (`historicoCongelado`). A tela de Relatórios mensais compara o extrato de hoje com o congelado no envio e marca "extrato mudou depois do envio" para sugerir reenvio. O motor (`accrual.ts`, puro e testado) parte desse último lançamento, vai até a maior data com taxa gravada, corta o tempo em segmentos de saldo parado (cada lançamento fecha um) e aplica o produto de `(1 + taxa/100)` dos dias úteis do intervalo **meio aberto** `(start, end]` — o dia em que um período fecha é o mesmo em que o próximo abre e a taxa dele conta uma vez. Só saldo positivo rende. O rendimento vira lançamento em `period_end`, então o segmento seguinte rende sobre ele sem tratamento especial. **O motor é independente de ordem** (reconstrói os segmentos a partir da linha do tempo), e é isso que permite que o fechamento automático dentro de `createVbEntries` seja conveniência e nunca derrube o lançamento. O botão "Calcular rendimento" mostra a prévia e só grava depois da confirmação, sempre recalculando no servidor. O cron diário do CDI **não lança rendimento**, só baixa taxas (uma linha por dia no extrato seria ilegível); a única gravação automática é o fechamento mensal do cron do dia 5. `npx tsx --conditions=react-server scripts/vb-cdi-rebuild.ts` (com `DRY=0`) apaga e refaz todos os rendimentos por CDI com as regras atuais do motor — é o caminho quando uma regra de corte muda. O índice único parcial `vb_entries_cdi_one_per_period` (credor + fim do período, só rendimento CDI aprovado) é a trava contra duplo clique ou duas execuções simultâneas: a segunda leva 23505 e a action responde "acabou de ser lançado por outra execução" — sem ele, o mesmo rendimento entraria duas vezes e não há exclusão de lançamento aprovado. `npx tsx scripts/vb-cdi-check.ts` compara o motor com um período já fechado do histórico.
- **Extrato mensal por e-mail (`/vb/relatorios`, `src/lib/vb/report/`)**: cada credor ativo recebe o extrato do mês (abertura, entradas, saídas, rendimento, linhas com saldo corrente, acumulado no ano). O extrato é a função pura `buildMonthlyStatement` (testada) e o e-mail é `renderVbMonthlyEmail` — HTML inline, sem `<style>`/`<svg>`, sem menção a planilha ou Omie; a prévia da tela renderiza o mesmo HTML num iframe. O **status é derivado, nunca gravado**: o banco só guarda os envios (`vb_report_sends`, com o extrato congelado em `statement`); `reportStatusFor` (puro, testado) decide `enviado` (há envio oficial/reenvio) > `sem_email` (`vb_creditors.email` nulo, definido na tela do credor) > `rendimento_pendente` (último rendimento termina antes do fim do mês e houve saldo positivo) > `pronto`. **Nada sai sozinho**: o cron `/api/cron/vb-monthly-reports` (dia 5, 09:00 BRT) só manda aos gestores do VB um resumo do mês anterior com o link; o envio ao credor é clique na tela (um, ou "Enviar todos os prontos"), destinatário sempre resolvido no servidor. Testar vai só para o e-mail da sessão com tarja, hora no assunto e `X-Entity-Ref-ID` (mesma separação do BI). Reenviar exige envio anterior e não apaga o primeiro registro.
- Escrita nas tabelas `vb_*` só pelo admin client depois de `requireVbGestor()` (`src/lib/vb/auth.ts`); leitura das páginas pelo client do usuário sob RLS (`vb_role()`).
- Fases seguintes previstas no modelo, não construídas: edição de lançamentos aprovados (hoje as únicas exclusões de aprovado são o Desvincular da triagem da Omie e o recálculo de rendimento CDI em lançamento retroativo).

### Módulo Caixa (`/caixa`)

Posição de caixa do grupo inteiro: saldo de todas as contas correntes de todas as empresas, lido da Omie. Primeira (e por ora única) tela: **Caixa Geral** (`/caixa/real` — chamava-se "Caixa Geral" até 21/09/2026; a URL, a chave de preferência `caixa_real` e os identificadores no código ficaram).

- **Acesso**: linha em `user_module_roles` (`module='caixa'`, `role='user'`) **OU** admin — modelo do Case/Contratos, não o do VB (lá admin não passa por cima). Marcável em "Módulos visíveis" na tela de Usuários, em qualquer perfil, inclusive `franqueado`/`csc`. Fonte de verdade: `src/lib/auth/caixa.ts`. O perfil `validador_contrato` segue ilha e não alcança.
- **Quem tem o módulo vê TODAS as empresas.** Este módulo **não** herda a regra de `restricted-companies.ts` (Dataforte) — decisão explícita do dono do projeto em 17/09/2026, não esquecimento. A pergunta que a tela responde ("quanto o grupo tem em caixa agora") só faz sentido com o grupo inteiro somado; esconder uma empresa devolveria um total errado sem avisar. Ao aplicar `restrictedCompanyIds` numa tela nova, **não** inclua o Caixa achando que ficou de fora por descuido.
- **A tela lê com service role**, depois do gate `getCaixaUser()` — mesmo enquadramento das páginas `/contratos`. O motivo é o embed `companies(name)`: `companies` tem RLS por `user_company_access`, então um usuário com o módulo mas sem vínculo veria nomes vazios ou perderia linhas, contradizendo a regra acima. As policies de `caixa_*` (`caixa_has_access()`) continuam valendo como segunda linha de defesa.
- **Saldo AQUI é gravado** — ao contrário do VB, onde o saldo é a soma dos lançamentos. Aqui é uma **observação externa** feita num instante: `caixa_accounts.saldo` + `saldo_at` guardam o corrente (leitura de uma query só) e `caixa_balance_snapshots` guarda cada captura, que é o que permite a "variação no dia" e auditar por que um número mudou. `caixa_sync_runs` registra cada execução.
- **`nSaldoAtual` da Omie é o saldo ao FIM DO PERÍODO PEDIDO, não "o saldo de agora".** Conferido contra produção em 17/09/2026 (`npx tsx scripts/caixa-omie-probe.ts --janelas`): a mesma conta devolveu 11.960,67 pedindo 18/08→18/08 e 7.445,80 pedindo até hoje. Por isso `dPeriodoFinal` é **sempre hoje (BRT)** em `src/lib/caixa/omie.ts`. Quem alargar o período achando que mexe só no tamanho do payload transforma o saldo da tela em histórico, sem quebrar nada e sem aviso. A janela hoje→hoje é também a mais barata (3 movimentos contra 66 numa de 30 dias).
- **Duas integrações distintas, que viram os dois botões da tela**: `ListarContasCorrentes` (`geral/contacorrente/`, 1 chamada por **empresa**, traz banco/agência/conta/tipo) alimenta "Sincronizar contas"; `ListarExtrato` (`financas/extrato/`, 1 chamada por **conta**) alimenta "Atualizar saldos". Conta que some da Omie vira `ativo=false`, nunca é apagada — os snapshots dela continuam sendo fatos.
- **A tela mostra contas ativas E inativas, com coluna Status e filtro padrão em "Ativa".** Conta encerrada na Omie nunca é apagada aqui (o histórico de saldo dela é fato), mas fica fora do recorte de abertura — o saldo dela não muda mais, e somá-la daria um caixa que não existe. A varredura de saldos cobre as **ativas sempre + as que nunca foram capturadas** (`saldo_at` nulo): assim a inativa recebe um número na primeira vez que é vista e nunca mais é consultada, em vez de custar duas chamadas por dia para sempre. Inativa que já foi ativa conserva o último saldo, congelado no fechamento. **Conta inativa não conta para o atalho "só as desatualizadas"** — ela nunca é atualizada, e incluí-la marcaria quase toda empresa como pendente.
- **A tela avisa quando a atualização falhou ou não rodou** (`src/lib/caixa/health.ts`, pura e testada; banner `sync-alert-banner.tsx`). Três estados, por prioridade: *morreu* (execução começou há >15 min e não terminou — teto da Vercel), *falhou* (terminou com empresa/conta em erro; cita as empresas e aponta o atalho "só as desatualizadas") e *não rodou* (o horário do cron passou com 45 min de folga e não há execução dele desde então). **Manual bem-sucedida apaga o "falhou" mas não o "não rodou"** — o problema deste é o cron parado, e continua verdadeiro depois de um clique. Os horários vêm de `schedule.ts` (`CAIXA_CRON_SLOTS_BRT`), que é a fonte para a tela e para o alerta, **mas o cron não lê daqui**: mudar horário exige editar o `vercel.json` junto. Não há e-mail — pedido do dono do projeto: o aviso é na tela.
- **As 5 empresas sem credencial Omie ficam de fora sem aviso na tela** (Salvaterra Estacionamento, Sirena, Viva Holding, Viva Uberaba, empresa de teste). Decisão de 17/09/2026: na Omie não são empresas separadas ou já foram inativadas; existem no sistema só pelo histórico do DRE. Não acrescente um "N empresas fora" achando que falta transparência.
- **Gráfico "Evolução do caixa"** (`caixa-history-chart.tsx` + `POST /api/caixa/history` + função SQL `caixa_history`, migration `20260918120000`). A tela manda os **ids das contas visíveis**, então a curva obedece a qualquer filtro sem que o endpoint conheça nenhum. A série é montada no banco com **carry-forward** (último saldo conhecido de cada conta até o dia): num dia em que uma empresa falhou na varredura, a conta dela não tem snapshot e, sem isso, cairia a zero — uma queda falsa. Dias anteriores à primeira captura ficam de fora (`HAVING`), então a série começa onde há dado. Janelas fechadas em 30/90/180/365 dias. Uma série só → sem legenda; mesmo hue do gráfico do VB (teal), grade em hairline sólida, texto em tokens de tinta. `--border` é componentes HSL (shadcn): em SVG use `hsl(var(--border))`, os outros tokens já são cor.
- **Os filtros são lembrados por usuário, sem botão Salvar** (`src/lib/caixa/prefs.ts`, puro e testado; tabela `user_preferences`, chave `caixa_real`, migration `20260921120000`). O que se guarda: filtros/faixas/ordenação da tabela (`FilterTableSnapshot`), a janela do gráfico e o escopo dos botões. Salva 800 ms depois da última mudança, só se a chave estável (`prefsKey`) mudou; o `user_id` vem da **sessão**, nunca do corpo (`PUT /api/caixa/prefs`). O padrão (ativas + dinheiro, 90 dias, todas as empresas) só vale para quem nunca salvou — depois disso, "Limpar tudo" salvo é o que a pessoa vê ao voltar, e por isso existe **"Voltar ao padrão"** na tela, ao lado do aviso "seus filtros ficam salvos" (quem abre já filtrado precisa saber por quê). O parser é campo a campo: JSON corrompido descarta a parte ruim e nunca trava alguém num filtro que não consegue tirar. Motivo do módulo: são ~3 usuários e cada um cuida de um conjunto de empresas — o recorte próprio é o uso normal, não a exceção. `user_preferences` é **genérica** (uma linha por usuário × chave, RLS `auth.uid()`): a próxima tela que precisar lembrar algo usa uma chave nova aqui, não outro truque em `user_module_roles`.
- **Os dois botões têm escopo escolhível** (`company-picker.tsx`): todas as empresas (padrão) ou algumas, com busca e o atalho "só as desatualizadas". Existe porque a varredura completa custa ~80s e o caso mais comum depois de uma falha é refazer só as duas que falharam. A lista vem do **servidor** (`listCaixaCompanyRefs`), não das linhas da tabela — empresa com credencial e ainda sem nenhuma conta sincronizada não aparece nas linhas, e é justamente ela que precisa do "Sincronizar contas". Escopo `null` = todas; Set vazio = nenhuma (botões desabilitados), a mesma convenção do filtro e pelas mesmas funções (`filter-logic.ts`). O escopo **não** mexe no que a tabela mostra.
- **A chamada de saldo é lenta: ~2,4s por conta**, muito acima dos 350ms do rate-limit. Números reais da primeira carga (17/09/2026): 26 empresas, 378 contas no cadastro, **272 ativas**, varredura de saldos em **121s com 5 em paralelo e 81s com 8** (o padrão hoje), medidos contra a Omie real — o de 81s pelo próprio endpoint do cron. Serializada seria ~650s, acima do teto de 300s da Vercel. Duas consequências no desenho, **não mexa nelas sem refazer a conta**: (1) `omieCall` aceita `opts.lastRequestRef`, um relógio de rate-limit **por empresa** (o limite da Omie é por `app_key`), e o cron roda 5 empresas em paralelo (`CAIXA_SWEEP_CONCURRENCY`); (2) os botões da tela varrem **uma empresa por requisição**, em sequência no cliente, com barra de progresso — nenhuma requisição chega perto do teto e a falha de uma unidade não perde o trabalho das outras.
- **Empresas**: ativas **com credencial Omie**. `sync_enabled` é ignorado de propósito — aquela flag decide se a unidade entra no ciclo do DRE/BI, e unidade fora do pacote de relatórios continua tendo dinheiro em conta.
- **A tela abre filtrada em DINHEIRO, e isso é a regra mais importante dela.** A Omie chama tudo de "conta corrente", inclusive cartão de crédito. Levantamento das 272 contas ativas (17/09/2026): `CC` conta corrente (112), `CX` caixa físico (75), `CA` aplicação (42), `CR` cartão de crédito (33), `CV` cartão/garantia (9), `PG` conta de pagamento (1). O filtro padrão é `CAIXA_TIPOS_LIQUIDOS` = `CC` + `CX` + `PG`; aplicação, cartão e garantia continuam na tabela, a um clique no chip "Tipo". **A diferença não é detalhe**: caixa = R$ 3,19 mi contra R$ 58,41 mi somando tudo — quase toda a diferença são R$ 55,0 mi em aplicações, e somar `CR` subtrairia fatura de cartão do caixa, respondendo "posição líquida" em vez de "quanto temos agora". Uma faixa abaixo dos cards nomeia o que ficou de fora e quanto, porque um total menor sem dizer o que foi excluído é o tipo de número que leva a decisão errada. **O total é SEMPRE a soma do que está na tela** — não crie um total que ignore o filtro, é esse invariante que torna a tela confiável.
- O filtro estilo Excel é o componente genérico `src/components/data-table/filter-table.tsx` (semântica pura e testada em `filter-logic.ts`: chave **ausente** = sem filtro, Set **vazio** = nada passa — conflar os dois quebra o gesto de desmarcar "(Selecionar tudo)" para escolher dois valores) (popover por coluna com busca + checkboxes, chips dos filtros ativos, ordenação). Duas regras dão a sensação certa: a lista de valores de uma coluna é calculada sobre as linhas que passam por **todas as outras** (filtrou Tipo, o popover de Empresa só oferece quem tem aquele tipo), e o "selecionar tudo" da seleção marca só o que está **filtrado**, com estado indeterminado — somar linha escondida no card seria erro silencioso. **O componente não conhece saldo nem empresa**; reaproveite em vez de copiar.
- Cliques repetidos em "Atualizar saldos" dentro de ~45s servem o cache de leitura do `omieCall` — é o que evita o bloqueio por "consumo redundante" da Omie (que este projeto tomou de verdade durante a Fase 0).

### Módulo Orçamento (`/orcamento`) — acesso

`src/lib/auth/orcamento.ts` é a fonte de verdade. O módulo nasceu admin-only em todas as camadas e foi aberto porque o processo real tem construtores (os **gerentes**, cada um nos seus setores) e a **diretoria**, que valida.

- **Concessão** numa linha de `user_module_roles` (`module='orcamento'`), marcável em "Módulos visíveis" na tela de Usuários — mesmo caminho de Caixa, Contratos e VB, nunca uma coluna `can_orcamento` em `users` (coluna nova exige migration, e até ela rodar o `select` explícito de `getSessionContext` quebra inteiro com 42703 e derruba o app). A sessão expõe como `profile.can_orcamento`. **Admin herda sem a linha**; `validador_contrato` é ilha e não alcança nem com ela.
- **O PAPEL vem do perfil, não de um cadastro novo**: `diretor` → `validador`; `gerente` ("Gerente Sócio") → `construtor_amplo` (lê a empresa inteira, edita os setores dele); `gerente_setor` ("Gerente") → `construtor` (só os setores dele). É a mesma distinção que já vale em `/ctrl/orcamento`, reaproveitada para não criar um terceiro vocabulário de papéis. O botão da tela de Usuários **só aparece para esses três + admin** (`isOrcamentoEligibleProfile`): marcar o módulo para um solicitante não daria acesso nenhum, e botão que não faz nada é pior que botão nenhum. Escape hatch: `role='construtor'|'validador'` na própria linha **sobrepõe o perfil** e só REDUZ privilégio — é o "ver como" (a tela grava sempre `'auto'`).
- **Quatro recortes, e eles se combinam**: o módulo (a concessão) diz *se entra*; o perfil diz *o que faz*; `user_company_access` (as "Unidades") diz *quais empresas*; e `orcamento_user_setores` diz *quais setores do orçamento dentro de cada empresa*. A RLS repete a mesma condição em `orcamento_has_access()` / `orcamento_pode_ler_empresa()` (migration `20260922120000`) — app e banco não podem divergir aqui.
- **As telas de CONFIGURAÇÃO seguem admin-only** mesmo para quem tem o módulo (`isOrcamentoConfigPath`): método por categoria, plano de cargos, encargos, setores, grupos e índices. Um gerente constrói o orçamento; ele não redefine as premissas dele.
- **Gerente e Gerente Sócio NÃO EDITAM Média nem Valor fixo** (`podeEditarMetodo`, em `metodos.ts`, testado) — nem o valor, nem o índice, nem os contratos. Os dois métodos partem de um número que o gestor não define (o realizado do ano anterior, o contrato) e são mantidos pela administração; o que o gestor constrói é **Pessoal** e **Planejamento dos gestores**. Eles seguem LENDO as duas telas — precisam do conjunto do setor, e é ali que mora o painel de validação. A regra é só do PAPEL: o recorte por SETOR continua por cima (`podeEscreverNoSetor`). Está nas 6 actions de escrita (4 em `media.ts`, 2 em `valor-fixo.ts`) **e** nas telas, que travam os campos e explicam por quê — campo travado sem explicação é o mesmo silêncio das telas vazias.

**O SETOR do Orçamento é POR EMPRESA, em cadastro próprio** (`orcamento_user_setores`, migration `20260929130000`). A mesma pessoa pode responder por Marketing numa empresa e por nada em outra — era impossível enquanto o recorte vinha de `user_sectors` (do Compras), que **não tem empresa** e por isso dava o mesmo setor em todas as unidades que ela alcança.

- **A atribuição guarda o NOME do setor do ORÇAMENTO**, não o id da linha nem o setor do Compras. As três âncoras possíveis, e por que o nome ganhou: o **id** de `orcamento_setores` vale para um ano só (a tabela é empresa × ano), o que obrigaria a refazer o cadastro de todo mundo a cada janeiro; o **`ctrl_sector_id`** é opcional — metade dos setores desta base não tem ponte, e eles ficariam inatingíveis — e, pior, `cloneSetores` copia os setores de um ano para o outro **só pelo nome, sem levar a ponte**, então o escopo se desfaria sozinho a cada ano clonado. O **nome dentro da empresa** é a identidade que o sistema já usa para atravessar anos. A regra de casamento é `setor-atribuicao.ts` (puro e testado), usada nos três pontos: gravar, resolver o escopo e diagnosticar a tela vazia — divergir em qualquer um deles dá escopo silenciosamente errado.
- **O preço do nome é o rename**: `renameSetor` carrega a atribuição junto (por empresa, `ilike` no nome antigo). Está na action e não em trigger, para o rastro ficar no código que se lê. É best-effort: o setor já foi renomeado, e derrubar a ação deixaria o cadastro pior.
- **A ponte `ctrl_sector_id` NÃO decide mais quem enxerga o quê.** O que sobrou para ela é `departamentoDoSetor`, que a usa para chegar ao departamento da Omie na semeadura da base do Planejamento. O aviso da tela de Setores mudou de tom junto — dizia que o gerente não enxergaria nada, o que virou mentira.
- **As empresas do bloco são as UNIDADES**, não uma segunda lista: `user_company_access` é o que `podeVerEmpresa` lê, e oferecer ali uma empresa fora dela produziria setor num lugar que a pessoa nem abre. Por isso o seletor de Unidades deixou de depender do Financeiro (`showCompanies` aceita `can_orcamento`) — um Gerente de Compras + Orçamento não tinha caminho para receber empresa nenhuma, e o painel do módulo abria vazio.
- **Os setores oferecidos são os do ORÇAMENTO daquela empresa** (de todos os anos, deduplicados por nome), não os 21 do Compras. Oferecer a lista do Compras era o defeito da primeira versão.
- **Gravar SUBSTITUI a atribuição inteira** (`setOrcamentoSetores` apaga e reinsere). Upsert puro não faria desmarcar funcionar: tirar um setor da tela não tiraria nada do banco e o escopo ficaria maior do que a tela mostra. Tirar o módulo limpa a atribuição junto — escopo de módulo que a pessoa não tem é cadastro invisível, que voltaria a valer sozinho numa reconcessão.
- Foi seguro trocar o modelo duas vezes no mesmo dia porque **ninguém tinha a concessão** (zero linhas em `user_module_roles` com `module='orcamento'`) e a primeira tabela estava vazia.

**O recorte falha em SILÊNCIO.** A corrente é `orcamento_user_setores` (usuário × empresa × nome) → `orcamento_setores` daquele ano, casando por nome. Quebrando qualquer elo, o escopo vira `[]` e as consultas viram `.in("setor_id", [])`, que **casa com nada e não devolve erro**: a pessoa vê tela em branco e conclui que o sistema quebrou. Consequências que não se deve "consertar" por engano:

- **`src/lib/orcamento/escopo.ts`** (puro e testado) transforma esse silêncio em frase, e `EscopoAlerta` a mostra no **layout do workspace** — uma vez, valendo para todas as abas, porque o recorte é o mesmo em todas e avisar só no hub deixaria a pessoa chegar na tela em branco pelo link direto. Os motivos apontam para cadastros DIFERENTES (usuário × setores da empresa × ponte × "os setores são de outra pessoa"), e a ordem das perguntas é a ordem do conserto: o aviso nomeia a primeira coisa que precisa acontecer, não a última. `diagnosticarEscopoDaEmpresa` lê com o **admin client** de propósito — é justamente quando o escopo está vazio que é preciso CONTAR o que existe para explicar por quê; sob a RLS do usuário tudo voltaria zero e o aviso não saberia distinguir os casos. Só números saem de lá.
- **Empresa com "Orçar por setor" DESLIGADA é admin-only na prática**: tudo cai no balde "Não atribuído", que não pertence a gerente nenhum (`podeEscreverNoSetor` recusa linha sem dono). Não é cadastro faltando — o aviso diz isso com todas as letras em vez de mandar ligar um vínculo que não existe.
- Lista de empresas vazia para quem não é admin quase nunca é "não há empresa": é o vínculo de **unidades** do usuário. O painel diz isso, em vez de "Nenhuma empresa ativa encontrada" — que faz a pessoa procurar defeito num cadastro que ela nem enxerga.

**O Planejamento dos gestores continua escondido de quem não é admin** (`METODOS_EM_VALIDACAO`, em `metodos.ts`) — conceder o módulo hoje entrega Pessoal, Média, Valor fixo e Prévia, não o Planejamento. Tirar a chave desse conjunto é o único lugar.

- `mapeamento` and `configuracoes` are **admin-only** even for other DRE users.

**Funções `SECURITY DEFINER` ignoram RLS, e no Supabase toda função nova nasce executável por `anon` e `authenticated`** (default privileges do projeto — um `DROP`+`CREATE` também zera revogações anteriores). Por isso, toda função `SECURITY DEFINER` que lê ou grava dados de empresa tem que terminar com `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated; GRANT EXECUTE ... TO service_role;` e ser chamada pelo app com o admin client. Só os predicados usados dentro de policies (`is_admin()`, `has_ctrl_role()`, `user_has_company_access()` etc.) ficam liberados para `authenticated`. A auditoria de 03/09/2026 (`20260903120000_security_hardening.sql`) fechou as existentes; uma migration posterior que recrie a função reabre o buraco sem aviso — `get_advisors` do MCP acusa como `authenticated_security_definer_function_executable`.

**Migrations**: timestamped, applied in order. `schema_migrations` records the *application* timestamp, which does **not** match the file-name prefix — match migrations by name, not by timestamp. Per Marcelo's global instructions, run DDL/DML yourself via the Supabase MCP or CLI rather than pasting SQL for him to run.

## Deployment

Vercel. Cron jobs (`vercel.json`):
- `/api/cron/sync-all` — `0 6 * * *` (06:00 UTC / 03:00 BRT). Omie sync. **On the BI generation day (BRT) it syncs the last 6 months** instead of the 3-day rolling window, so retroactive entries land before the monthly reports are generated. Emails admin on sync failures and unmapped categories.
- `/api/cron/process-contracts` — `*/2 * * * *`. Drains the contract-extraction batch queue.
- `/api/cron/bi-monthly-validation` — `0 12 5 * *` (12:00 UTC / **09:00 BRT**). Generates the previous month's BI report per company (only companies with recipients in `bi_report_subscriptions` **and** `sync_enabled` not false — unidade fora do pacote não entra no ciclo), stores it in `bi_report_validations` as `pendente_validacao`, and notifies CSC users. **Does not send.**
- `/api/cron/bi-monthly-autosend` — `0 12 11 * *` (12:00 UTC / **09:00 BRT** — cron da Vercel é sempre UTC; não é meio-dia de Brasília). Sends (via Resend) every previous-month report still unsent. Reports `em_revisao` or without content are *not* sent — they raise an admin alert instead. Destinatário é resolvido **no momento do envio**, então mexer na lista em Plataforma > Relatório BI depois da geração muda quem recebe; empresa que ficou sem destinatário falha o envio.
- `/api/cron/ctrl-approval-reminders` — `0 13 * * 1-5` (13:00 UTC / **10:00 BRT, segunda a sexta**). Lembrete diário de aprovações do módulo Compras (ver abaixo).
- `/api/cron/vb-cdi` — `0 11 * * 1-5` (08:00 BRT). Baixa o CDI do Banco Central para o VB; não lança rendimento.
- `/api/cron/vb-monthly-reports` — `0 12 5 * *` (09:00 BRT, dia 5). Fecha o rendimento CDI do mês anterior (última linha em `vb_entries` por credor) e avisa os gestores do VB que os extratos estão disponíveis em `/vb/relatorios`; **não envia ao credor**.
- `/api/cron/caixa-saldos` — `0 7 * * *` (04:00 BRT) e `30 15 * * *` (12:30 BRT). Saldos do módulo Caixa. **A execução da madrugada também espelha o CADASTRO** antes dos saldos, para que uma conta nova apareça sozinha na manhã seguinte (o botão da tela vira conveniência). O corte entre as duas é por **hora de Brasília**, não UTC — às 04:00 BRT o servidor já está em 07:00 UTC. `?cadastro=1` força o espelho do cadastro em qualquer horário.
- `/api/cron/monthly-report` — AI monthly executive report (invoked on schedule/manually).

Os dois dias da rotina (geração e envio automático) vivem em `src/lib/financeiro/relatorios/schedule.ts` — `BI_GENERATION_DAY` / `BI_AUTOSEND_DAY`. Todo texto de tela, notificação e e-mail lê de lá; **o cron não lê constante**, então mudar um dia exige editar `vercel.json` junto (e conferir que a janela de 6 meses do `sync-all` casa com o dia da geração). Não escreva o número do dia à mão em texto novo.

There is **no direct dispatch**. The legacy `/api/cron/monthly-bi-report` (direct send to `bi_report_subscriptions`, bypassing validation) was deleted — do not recreate it. `/admin/relatorios-bi` ("Relatórios BI") now only defines *who receives*; the validation flow below is the official send. The one remaining bypass is the admin-only `POST /api/bi-subscriptions/send` ("Enviar agora"), kept as manual contingency for a single manager.

### BI report validation flow (CSC)

`Financeiro > Validação Relatório` (`/financeiro/validacao-relatorio`) is the human gate between generation and delivery. Access whitelist lives in `src/lib/auth/bi-validation.ts` (profile `csc`, admin, and two named e-mails) and is mirrored by `public.can_validate_bi_reports()` in RLS. Actions: **Aceitar** (unlocks 1-click send), **Revisão** (blocks send, records who/when/why), **Adicionar contexto** (free text → re-runs the AI analysis with the context; numbers never change), **Histórico de contexto** (read-only list of every context ever added to that company × month — text, author, timestamp, and the report version it was applied to; served by `GET /api/bi-validation/[id]/contextos` from `bi_report_validation_contexts`). Context **accumulates**: each new text is appended to `extra_context`, so the history is what tells the CSC what is already in the prompt. The history stays available after the send and when generation failed.

**Depois do envio a linha tem duas ações: Testar e Reenviar.** Antes ficava sem nenhuma. **Testar** (`action: "teste"`, `sendValidationTestEmail`) manda o e-mail idêntico ao do gestor, **só para o e-mail da SESSÃO** — o destinatário nunca vem do corpo da requisição, senão a rota viraria um meio de mandar o resultado de qualquer empresa para fora. Não é envio: não mexe em `status`, `sent_at` nem em `ai_reports`, e o único rastro é o evento `envio_teste`. Funciona com o relatório enviado ou não, e é o caminho para conferir renderização (os gráficos são imagem inline, e cada cliente de e-mail trata imagem de um jeito) sem incomodar ninguém. **Três coisas separam o teste do envio oficial na caixa de quem dispara os dois** — não remova nenhuma achando que é redundância: assunto com data/hora (`[TESTE 10/09 14:03] …`), tarja âmbar no topo do corpo (parâmetro `banner` de `renderOnePageEmail`, que o envio oficial não usa) e o cabeçalho `X-Entity-Ref-ID` único. O cabeçalho é o que de fato impede o Gmail de agrupar; um prefixo `[TESTE]` sozinho **não** resolve, porque cliente de e-mail trata colchete no início como etiqueta de lista e ignora ao montar a conversa — o efeito prático era o envio oficial aparecer dentro da thread do teste, exibindo o título "[TESTE]" e assustando quem enviou. **Enviar aos novos** (`action: "enviar_novos"`, `onlyNewRecipients: true`) resolve o "esqueci de cadastrar fulano": manda só para a diferença entre o cadastro atual de Plataforma > Relatório BI e o `sent_recipients` já gravado, então quem já recebeu não leva o mesmo relatório duas vezes. O botão só aparece quando essa diferença existe, e a lista é **recalculada no servidor** antes de disparar — o cliente não escolhe destinatário (a regra "recipients sempre resolvidos no servidor" continua valendo; não existe caminho para digitar um e-mail avulso). O `sent_recipients` **acumula** nesse envio (union), senão os antigos voltariam a contar como novos no clique seguinte. Evento: `enviado_novos`. **Reenviar** (`action: "reenviar"`, `allowResend: true`) libera conscientemente a trava de duplicidade — que existe porque o envio manual e o cron do autosend podem cair no mesmo relatório — e exige confirmação na tela, com a lista de destinatários à vista. O reenvio **não sobrescreve** `sent_at`/`sent_by`/`status`: a data do primeiro envio é auditoria; cada reenvio vira um evento `reenviado_manual`. Ao mexer nisso, lembre que `bi_report_validations.status` tem CHECK com lista fixa (não invente valor novo), enquanto `bi_report_validation_events.action` é texto livre.

**O contexto também RETIFICA, não só complementa.** `CONTEXTO_CONTROLADORIA_RULE` manda a IA reler os próprios alertas e ações depois de ler o contexto: alerta que o contexto desmonta não é gerado; alerta que sobrevive vem com a ressalva no próprio texto (inclusive quando a causa reaparece dentro de um alerta agregado, ex.: "receita líquida abaixo do orçado, impactada por formaturas"); ação já tomada ou desnecessária sai da lista, trocada pelo próximo passo real; severidade é recalibrada. A regeneração é **stateless** — a IA não vê a versão anterior do relatório, então o contexto precisa descrever o problema ("não havia formatura prevista em julho; o orçamento foi rateado linearmente"), não apenas apontar o item ("o alerta 2 está errado").

**O contexto vive dentro do `diagnosticoPrincipal` — não crie um bloco só para ele.** É o único texto que todo template renderiza (`show("diagnostico")` vale para todos, e Viva/genérico nem filtram blocos), por isso o prompt manda escrever de 3 a 5 frases costurando leitura do período + explicação num texto único; o cap do campo é 1200 chars por causa disso (era 900 — contexto que pedia uma análise a mais dentro do diagnóstico estourava e derrubava a geração inteira). O limite tem de estar em **três** lugares em sincronia: o `max()` no schema, a regra 2.0 do `CONTEXTO_CONTROLADORIA_RULE` e a menção na seção de venda de unidade — o provedor ativo (DeepSeek) responde em `json_object`, sem validação de tamanho do lado dele, então quem segura o limite é o texto do prompt. Estourando mesmo assim, o retry do `one-page-analyzer` devolve ao modelo o campo, o tamanho escrito e o limite (`describeSchemaIssues`); nudge genérico não corrige estouro de tamanho. Um bloco separado ("Contexto do período") chegou a existir e foi removido: o texto aparecia duas vezes, já que o diagnóstico também o traz. Cuidado ao mandar a explicação para outros campos: `destaques` só chega ao leitor pelo bloco de alertas, que prioriza riscos e **corta em 3 cards** (`mapAlertas`), e `leituraPorIndicador`/`justificativa` não são renderizados em lugar nenhum.

**Custos variáveis lidos junto com a receita (7 empresas).** `custos-variaveis-receita.ts` decide se `CUSTOS_VARIAVEIS_RECEITA_RULE` entra no system prompt. Em Sirena, Terrazzo, Salvaterra Estacionamento, SGX, Village, Spot e Express, Custos de Serviços Prestados + IRPJ/CSLL/PIS/COFINS são **variáveis**: com a receita abaixo do orçado, a queda deles é consequência do faturamento que não ocorreu, não economia — sem a regra o `SHARED_TAIL` ("custo abaixo do orçado = FAVORÁVEL") fazia a IA celebrar como eficiência o reflexo de uma receita que não aconteceu. A regra **não** move essas linhas para `pontosAtencao` (o alerta continua sendo a receita, nunca o custo que deixou de ocorrer) e não alcança as despesas operacionais fixas. O gate é uma **allowlist própria, não uma flag em `ReportTemplate`**: a Express não tem template e cai no `genericTemplate`, compartilhado com toda empresa sem template — uma flag ligaria a regra para todas elas. A blocklist (Franquias Viva inteiro, Case Shows, Feat, Young Med, Salvaterra Condomínio) é redundante de propósito e falha fechada.

**O contexto precisa ser autorizado no system prompt, não só anexado ao user prompt.** O `SHARED_TAIL` de `one-page-prompt.ts` manda, em "REGRAS INVIOLÁVEIS", nunca citar eventos/nomes fora do JSON e justificar ações só nos indicadores — diante do conflito o modelo obedecia a regra inviolável e **descartava** o texto do CSC (Terrazzo, jul/2026: IPTU contestado judicialmente não saiu no relatório). Por isso `resolveOnePageSystemPrompt(input, { hasBusinessContext })` anexa `CONTEXTO_CONTROLADORIA_RULE`, que abre a exceção e torna o uso obrigatório. Segue o padrão do `INDICADORES_RELATORIO_RULE`: só entra quando há contexto, então o prompt de todo relatório sem contexto continua byte a byte o mesmo. Ao endurecer as regras invioláveis, cheque se a nova regra não volta a proibir o contexto.

The e-mail is rendered from `OnePageReportPreviewData` — the *same* object the screen renders — by `one-page-email.ts`. That is what keeps the e-mail identical to the BI screen per company (block allowlist, template-exclusive blocks, hidden fields). Do not add a second renderer fed from the raw payload.

**Os gráficos do e-mail são PNG inline, e `renderOnePageEmail` é async devolvendo `{ html, attachments }`.** Cliente de e-mail não roda recharts e o Gmail remove `<svg>`, então cada gráfico é desenhado em SVG (`one-page-chart-svg.ts`, puro) e rasterizado por `@resvg/resvg-wasm` (`one-page-chart-png.ts`), entrando no HTML como `<img src="cid:...">`. **Quem chama TEM de repassar `attachments` ao `sendEmailViaResend`** — esquecer isso não quebra o build nem o envio: o relatório chega com todas as imagens quebradas. O wrapper do Resend converte o Buffer para base64 (o SDK não faz isso no envio; Buffer cru viraria `{"type":"Buffer"}`). Escolhemos o WASM em vez do `@resvg/resvg-js` nativo porque o `package-lock.json` é gerado no Windows e o binário linux da Vercel ficaria de fora. O `.wasm` e os `.woff2` do IBM Plex são lidos do disco em runtime, então dependem de `outputFileTracingIncludes` no `next.config.mjs` (mesmo tratamento do pdfkit) — **rota nova que envie o relatório precisa entrar nessa lista**. Sem os arquivos, `svgToPng` devolve `null` e cada bloco cai no HTML de tabela que existia antes: o envio não quebra, mas os gráficos somem sem nenhum erro. Todo `<img>` leva `alt` com os números, para quem bloqueia imagem.

Recipients are always resolved server-side from the validation row's `company_id`; the client only sends the row id.

O **PDF** da prévia (botão "Baixar PDF", no topo do diálogo do olho) e o da tela de Business Intelligence saem do mesmo lugar: `exportOnePageReportPdf` em `src/lib/financeiro/relatorios/export-one-page-pdf.ts` — html2canvas sobre a folha `.one-page-report` já renderizada + jsPDF, com as libs em import dinâmico (ficam fora do bundle inicial). As duas telas capturam o mesmo componente, então o arquivo é idêntico; não crie um segundo exportador.

### Lembrete diário de aprovações (CTRL / Compras)

`src/lib/ctrl/approval-reminders/` + `/api/cron/ctrl-approval-reminders`. Às 10h BRT, **de segunda a sexta**, envia via Resend **um e-mail por aprovador** com todas as requisições que dependem da aprovação dele. Quem não tem pendência não recebe nada.

O fim de semana é excluído em **dois lugares de propósito**: no agendamento (`0 13 * * 1-5`) e dentro da rotina (`isWeekendBR` sobre o dia em Brasília, não em UTC — às 22h de domingo o servidor em UTC já é segunda). Assim uma execução manual num sábado também não dispara; `?force=1` é a saída consciente e `?dryRun=1` monta o conteúdo em qualquer dia.

Quem recebe o quê é derivado da mesma fonte de verdade da tela de Aprovações — não replique a regra em outro lugar:
- a **etapa vem do status**: `pendente` → gerente/gerente sócio; `pendente_diretor` → diretor. Como `applyApprovalStep` só move para `pendente_diretor` depois do aval do gerente, o diretor nunca é notificado antes da etapa gerencial;
- **notificação é sempre limitada pelo setor, inclusive para o diretor**: ele *aprova* qualquer setor (`hasGlobalVisibility`), mas só *recebe e-mail* dos setores cadastrados para ele na tela de Usuários (`user_sectors`). Decisão de negócio — não confunda com a visibilidade da tela. Gerente segue o mesmo filtro, com o fallback "sem vínculo recebe tudo" do `getRequests`;
- valem os overrides de `routing.ts`: `APPROVAL_ROUTING` (diretor/gerente fixo) e `approverSectorRestrictionFor` (alçada, falha fechada). **`DIRECTOR_HIGHLIGHT_SECTORS` agora tem dois efeitos**: além do destaque na tela, coloca o e-mail listado na etapa do diretor da rotina, restrito àqueles setores (é assim que `marcelo@quokka.net.br`, perfil admin, recebe TI / Financeiro Cash Out / Financeiro CSC / Diretoria — este último entrou em 10/08/2026 porque o setor era roteado direto ao diretor sem ninguém vinculado, e o e-mail ficava órfão);
- o pool sai de `users.profile` (`gerente`, `gerente_setor`, `diretor` + `can_compras` + `active`), **não** de `user_module_roles` — a tabela legada ainda guarda papéis de quem hoje tem outro perfil. Admin não recebe por ser admin, só via `DIRECTOR_HIGHLIGHT_SECTORS`.

`ctrl_approval_email_log` (unique `user_id` + `run_date` em BRT) é o rastro e a trava de duplicidade: reexecutar o endpoint no mesmo dia não reenvia. `?dryRun=1` monta sem enviar; `?force=1` reenvia conscientemente. Requisição pendente sem nenhum aprovador elegível não some: entra em `orphans` e vira alerta ao `ADMIN_EMAIL` — é o sintoma normal de setor sem gerente/diretor cadastrado, já que o filtro por setor não tem fallback global. A "mensagem do dia" é sorteada por hash de (usuário, dia) excluindo as últimas frases do log — determinística, então um reprocessamento repete a frase que o usuário viu.

All cron endpoints require `Authorization: Bearer <CRON_SECRET>`.

## Environment Variables

Required: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ENCRYPTION_KEY`, `RESEND_API_KEY`, `ADMIN_EMAIL`, `CRON_SECRET`, `NEXT_PUBLIC_APP_URL`.

O remetente do Resend tem **default no código** (`bi@contato.quokka.net.br`, domínio verificado do grupo, em `src/lib/email/resend.ts`) — `RESEND_FROM` só existe para trocá-lo. Não volte a exigir a variável: o Resend não aceita remetente genérico, então "só a chave configurada" já derrubou relatório aceito pelo CSC e a rotina de envio automático, sem que ninguém percebesse até o clique em Enviar.

Feature-specific: `OPENAI_API_KEY` (AI reports + contract LLM + Viagens web-price search), `APIDEVOOS_API_KEY` (Viagens — real flight prices via apidevoos.dev), `VISION_AGENT_API_KEY` (LandingAI contract OCR), `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON` + `FEAT_PRODUCOES_SHEET_ID`/`FEAT_PRODUCOES_SHEET_TAB` + `TERRAZZO_SHEET_ID` (Sheets sync; `TERRAZZO_SHEETS_SYNC_DISABLED` to disable).

`ENCRYPTION_KEY` is used for AES-256-GCM encryption of Omie credentials. Changing it after data is encrypted will break decryption — restore the original key or re-enter credentials.

## Conventions

- User-facing text and error messages in Portuguese
- Technical/debug messages in English
- Pages are async server components; interactive UI uses `"use client"`
- API routes return `{ error: string }` with appropriate HTTP status on failure
- Database migrations are timestamped and applied in order via `supabase db push`
- Omie API rate limit: 350ms between calls (`REQUEST_INTERVAL_MS`)
